Finding & tracking targets

Find the range’s target actors, then inspect the component that actually moves.

Discover targets

The inspected range uses TargetBase_C and derived classes. Get the active world from the viewport, then query that world:

local H = require("UEHelpers")

ExecuteInGameThread(function()
    local viewport = H.GetGameViewportClient()
    if not viewport or not viewport:IsValid() then return end
    local world = viewport:GetWorld()
    if not world or not world:IsValid() then return end

    local class = LoadAsset(
        "/Game/BlueprintLogic/Targets/TargetBase.TargetBase_C"
    )
    if not class or not class:IsValid() then return end
    local gameplay = StaticFindObject("/Script/Engine.Default__GameplayStatics")
    local targets = {}
    gameplay:GetAllActorsOfClass(world, class, targets)
    print("[MyMod] Targets found: " .. #targets .. "\n")
end

Actor versus component motion

A physics mesh can move while its owning actor’s transform stays unchanged. Capturing only K2_GetActorLocation can therefore show a target standing upright remotely while its mesh has fallen over locally.

Inspect the primitive, static-mesh or skeletal-mesh component that carries the visible body. Capture its world transform separately. Different target classes can need different component selection.

Sampling and caching

Discover actors infrequently and sample known targets on a bounded budget. Give moving and recently hit targets priority. A local registry once contained hundreds of targets; rediscovering or loading assets for every target on every frame is unnecessary.

Invalidate the registry after travel. Runtime addresses identify local objects only; they are not stable network IDs.

Resetting targets

Clearing HasBeenHit alone does not restore a broken target, a displaced physics body, its collision, or a reduced score value. A complete reset needs the original state of each relevant field and component. Restarting the range can be a more reliable first reset implementation.

Walkthrough: build a target registry

1. Enter a known range

Use the normal range flow and confirm the actual loaded level. A menu world can have no targets, and a table row named after a range does not prove that range was loaded. Resolve the world through the current viewport before querying actors.

2. Discover once and inspect a few examples

Get actors of the known base class, then log a bounded sample of full names and actual classes. A derived class can have a different body component, physics setup or hit implementation. Keep a registry with an explicit cap and explain what happens if the cap is exceeded.

3. Select the visible body

Enumerate primitive components and identify the mesh that represents the moving target. Record its component name, class and initial world transform. Avoid selecting an unrelated trigger box only because it is the first primitive component returned.

For a falling pan or moving figure, compare actor location and mesh location while the motion occurs. If only the mesh moves, actor-only replication will visibly fail even though the actor transform is being sent correctly.

4. Save a plain-data baseline

Store copied transforms and the specific flags your mode needs: hit state, value, hidden/collision state and physics state where relevant. Keep the live object reference separately and invalidate it with the world.

A baseline is a record of what you observed. It is not a guarantee that resetting those fields is sufficient for every target class; some targets can have additional state or event dependencies.

5. Update with a bounded budget

Carry a cursor through ordinary entries and separately sample moving/recently hit entries with a cap. Record the worst time between samples for an ordinary target. A registry of hundreds of targets makes that delay measurable; “we update some targets each tick” is not enough to judge motion quality.

If you interpolate a remote component, keep its render pose separate from the received authoritative sample. Treat a teleport or reset as a discontinuity rather than interpolating through the entire range.

6. Verify reset behaviour

Hit a normal target, hit a one-shot target, knock over a physics target and trigger a breakable target separately. Compare their required reset state. If a complete reset is not understood, implement a range restart instead of offering a reset button that restores only a flag.

Value and presentation can diverge

A target’s current HitValue can decrease after an accepted hit. A custom challenge may deliberately use a value captured at round start for fairness. Document which policy you chose. Reading a new value after applying the game’s hit reduction can otherwise score the wrong amount.

For one-hit targets, check both ValidForOneHitOnly and HasBeenHit. For hidden or destroyed targets, reject further custom hit processing rather than awarding points from a stale registry entry.

Lifetime tests

  1. Discover and count in the known world.
  2. Capture a body transform before and during motion.
  3. Trigger a valid hit and verify the expected state change.
  4. Restart the range and build a fresh registry.
  5. Confirm no old-world actor is sampled or mutated.

What was checked

Local discovery, target baselines, distinct synthetic targets and actor/component motion were tested. The documented registry strategy is a mod implementation, not a built-in replication service.
