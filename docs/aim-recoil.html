Aiming, cameras & recoil

Separate player aim, camera view, weapon pose, grip state and recoil modifiers.

1. Identify the layer you mean

LayerQuestion
Input / pawn aimDid the player request or enter an aiming state?
CameraWhat view rotation and field of view is being rendered?
Weapon poseWhere is the live weapon or cosmetic proxy positioned?
Grip / shoulderWhich handling context contributes to behaviour?
Recoil modifiersWhich aggregate values the weapon exposes in this build?

Changing a camera value is not automatically equivalent to the normal aiming action. Likewise, rotating a friend’s proxy is presentation, not another fully simulated weapon.

2. Read the aiming entry points

The inspected weapon base includes SetAiming with a NewAiming boolean, plus CosmeticSetAiming and CosmeticUnsetAiming. The shooter class also has its own SetAiming path. Similar names at different layers are a reason to observe the normal call sequence before invoking one manually.

The local outgoing pose capture read pawn.Aiming and the controller’s control rotation. These are concrete implementation choices, not proof that one field describes every camera/stance mode.

3. Compare camera and controller rotation

Resolve the current player camera manager from the current world when the feature depends on the rendered view. Compare it with control rotation if the effect follows aim. Camera offsets, weapon sway and transitions can make a single rotation source inappropriate for every visual.

For a muzzle effect, use the muzzle’s actual source location when available. A line projected from the camera is a useful fallback only if documented as cosmetic; it is not the true ballistic trajectory.

4. Inspect modifiers without replacing the whole model

The native weapon base exposes getter names for translation/torque absorption, secondary-grip strength, recoil restabilisation and control. Several are only dump-observed entry points in this reference. Do not write arbitrary values to them or assume a getter name reveals the complete recoil equation.

Record the selected grip/shoulder state, equipped parts and raw aggregate values. Use the baseline/remove/restore method from Weapon stats so a normal contextual difference is not mistaken for accumulated corruption.

5. Give remote handling a bounded presentation

Use explicit states such as aiming, firing and reloading on the visual proxy. Interpolate an aim pitch within a chosen supported range, retire old states on weapon/world changes, and keep this separate from the local gun’s real mechanics.

Walking or handling animations require suitable assets and a valid pose-driving path. Moving a primitive proxy smoothly does not establish a complete skeletal animation system.

Verify the transitions

  • Hip-to-aim and aim-to-hip follow the normal input.
  • Camera, gun and proxy do not drift into different spaces.
  • Grip/shoulder changes are recorded in stat comparisons.
  • Switching guns cancels old handling state.
  • Rapid fire/reload events remain attributed to the right gun.
  • Travel reconstructs both local usable and remote visible weapons.
