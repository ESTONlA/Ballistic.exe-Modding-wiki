Reading data tables

Find the table, inspect a row, and keep discovery separate from mutation.

Find a table

The demo has tables for attachment mount definitions and range menu data. You can inspect them once the asset is loaded:

ExecuteInGameThread(function()
    local data = LoadAsset("/Game/Data/Ranges/RangeData.RangeData")
    if not data or not data:IsValid() then return end

    local names = data:GetRowNames()
    for i = 1, #names do
        print("[MyMod] Range row: " .. tostring(names[i]) .. "\n")
    end
end

Read a row

In the tested loader, FindRow accepted a Lua string as the row name. Passing an FName in that particular call returned no row. This is different from APIs that explicitly expect an FName.

local row = data:FindRow("PistolRange")
if row then
    local map = row.MapName_3_02B8F3864CDF2B67468FDD80A1766519
    print("[MyMod] Map: " .. map:ToString() .. "\n")
end

The long suffix belongs to a Blueprint struct field. Copy the field name from your build’s dump instead of shortening it to MapName and assuming that will work.

The attachment table contained 86 mount rows in the inspected build. That is a build observation, not a constant your mod should require forever.

Watch the field types

A row can contain names, text, class references and soft class references. A soft reference is not the same thing as a loaded class. Converting, loading or iterating them can trigger additional engine work.

Keep an initial probe small: list names, read one known row, then inspect one field. Don’t start by copying the entire table into Lua.

Before changing data

Changing a row affects every consumer that reads the live table. Rewriting recursive mount relationships can also introduce cycles. A previous broad attachment-row copying experiment froze the game; a targeted lookup hook was used instead.

Make any edits reversible, preserve original values and test teardown. Adding a menu row doesn’t create its map or asset. See Range menus & travel.

Walkthrough: document one table field

1. List names without changing rows

Run the row-name example in a read-only test and save a bounded log. Confirm the table is valid and the result count is plausible. Treat the count as a discovery result; a hardcoded 86-row assertion is appropriate only for a fixture tied to that exact build, not for every future installation.

2. Pick one known row

Use a row the normal game menu already displays. In the local demo, PistolRange was useful because the menu and actual pool destination were known. Record the exact string and whether FindRow accepts the representation you passed.

3. Read the schema next to the field

A Blueprint-generated struct’s display label can differ from its reflected property identifier. Look for the full generated field name and property type in the dump. In a range row, a MapName field is a name; a Displayname field is text. Both can be converted for logging, but that does not make their original types interchangeable.

4. Compare the row with the UI

Verify that the row’s label appears where expected and that selecting it reaches the recorded package. If the card is absent, inspect unlock filtering and menu construction. If the card is visible but travel fails, inspect destination availability instead. Those failures occur at different layers.

This is more useful than publishing a large unannotated dump. It tells another modder which representation worked and which visible behaviour confirmed the interpretation.

Copy plain values, not the entire row

For a menu list, extract only the ordinary fields your feature needs, such as a display string and a verified destination ID. Keep soft-reference loading out of a broad initial dump. An accessor that is safe on one name field does not prove that every nested soft class array can be copied safely.

If you mutate a row, keep the original values and a precise restoration path. Never assume that disabling your mod automatically rolls back a live table change or data already persisted by the game.
