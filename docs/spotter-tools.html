Spotter cameras & range probes

Use the spotter’s own target and probe state to build diagnostics without confusing it with the shooter camera.

Find the active spotter

The names below are recorded in the local object snapshot dated 10 October 2026. That snapshot does not identify its game build. Resolve the same names in your current build before using them; the investigation steps below are not a report that every operation was tested.

The native Spotter class declares TargetsInLevel and GetClosestTarget. The Blueprint Spotter_C adds camera, target, distance-probe and display state. The scene can contain inactive spotters or CCTV references, so finding a class instance is not enough to prove the player is using it. Record possession and current target before attaching an overlay.

Make a read-only target card

  1. Enter the normal spotter view and select a target through the game.
  2. Record current target, pointed target and probe output together with a sample timestamp.
  3. Copy display data into ordinary Lua values at a bounded interval.
  4. Update your UI only when the target or displayed values change.
  5. Leave the spotter, change ranges and re-enter; clear old references and rebuild the card.

Do not overstate the accuracy display

A target-size or expected-accuracy visualisation is a display model. It is not proof that every future shot will land within the shown area. Compare the result with a controlled group of real shots using the same gun, ammunition and aiming state. Label a predicted area separately from observed impacts, and retain misses in the comparison.

Sharing spotter information

A remote spotter tool can send a target ID, measured range and a bounded text note. It should not send a UObject pointer or arbitrary object path for the receiver to call. Associate the note with the current range epoch, and show the sender and sample age. If the host changes ranges, discard the old observation rather than pinning it to a different target with a reused numeric ID.
