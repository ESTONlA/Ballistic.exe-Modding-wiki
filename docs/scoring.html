Hits & scoring

Count one valid gameplay event once, and keep your own score separate from progression.

Target callbacks

The observed OnHit signature passes ValidHit, player, impact information, hit energy, hit velocity, bonus flag, cartridge-unlock flag and breaking-hit flag. Character targets have their own matching hook path in the inspected build.

Inspect validity before scoring. Registering both base and derived handlers without attribution or deduplication can count a single physical shot more than once.

Attribute a hit

  1. Give each local firing event a monotonically increasing shot ID.
  2. Associate created bullet actors with that shot.
  3. Use the target’s hit path to connect the bullet and target.
  4. Check valid-hit state before adding a score.
  5. Retire old shot and bullet references after a short bounded window.

Do not attribute every hit to “the most recent shot” when the weapon can have several projectiles in flight. Two players firing at once makes that mistake especially visible.

Deduplicate events

For a custom per-target hit score, one useful key is round + player + shot + target. Decide explicitly whether pellets or repeated contacts should score independently for your mode. Deduplication policy is game design, not just a networking detail.

-- Custom mode state, not the game's persistent score.
local seen = {}
local score = 0

local function award(roundId, playerId, shotId, targetId, points)
    local key = table.concat({roundId, playerId, shotId, targetId}, ":")
    if seen[key] then return false end
    if type(points) ~= "number" or points ~= points then return false end
    if points < 0 or points > 100000 then return false end
    seen[key] = true
    score = score + math.floor(points)
    return true
end

Cosmetics are not rewards

A replicated impact can play a reaction without replaying the full local scoring/reward event. The local target fixture used CosmeticOnHit for visual response, with custom score handled separately. That does not make the function a complete substitute for the game’s normal hit logic.

Do not replay the ordinary hit event merely to display a remote impact: it may grant progression, unlock ammunition or change target value again.

Round timing

Use explicit countdown, playing, settling and finished phases. For network play, define whether a hit near the deadline is accepted by host receipt time, synchronised event time or a bounded grace policy. Cancel or pause when the connection changes instead of letting an invisible round keep running.

Walkthrough: design a small scoring mode

1. Write the rules before the hook

Decide whether a score is per projectile, per shot, per target or per round. Decide how repeated hits and pellets behave, whether a spent target scores again, and whether a target’s value is fixed at round start or read live. These rules determine your identifiers and deduplication key.

2. Log eligible events without awarding

Observe firing and target callbacks. Record player identity, shot ID, target identity, valid-hit state and event time. Confirm the same physical action is not entering both a base and derived handler as two awards.

Start with one player and one target, then two distinct targets, then rapid shots. Networking should come after local attribution is understandable.

3. Keep custom score in pure state

Use a Lua state object for round ID, phase, totals and the seen-event set. Do not store a custom challenge’s points in an unrelated game progression field just because it is already visible somewhere.

Validate finite bounded numbers before adding them. Reject malformed IDs and stale round identifiers. Define a maximum session total if packets or logs use a limited numeric representation.

4. Implement explicit phases

PhaseAllowed behaviour
CountdownShow the start time; do not award the competitive round yet.
PlayingAccept eligible shots and valid hit events.
SettlingAccept only events permitted by the documented end-of-round timing policy.
FinishedShow result and permit a rematch action.
CancelledExplain the interruption and require an explicit restart.

A settling phase is not permission to accept arbitrary late points. Preserve the event’s original eligible time, round identity and a bounded acceptance window. The local implementation has such a policy; internet fairness still needs real delayed-peer testing.

5. Choose score authority

For a host-authoritative challenge, the guest submits an attributed event and the host decides whether to apply it. Both peers display the host’s accepted round state. The guest should not independently overwrite the shared total when another snapshot arrives.

Connection to Steam does not supply this rule automatically. It is part of the gameplay protocol you implement.

6. Handle interruptions and rematches

Cancel or pause when a participant disconnects, becomes unready or leaves the world. Include the reason in the displayed state. On rematch, increment round identity and clear the relevant dedupe state so an old packet cannot award points to the new round.

Acceptance cases

Test an ordinary hit, an invalid hit, a duplicate event, an already-spent target, two players hitting the same target, a stale round, a hit near the deadline and a reconnect. Confirm cosmetic effects do not grant points twice and a rematch begins with new identifiers.

Keep screenshots of the displayed result and a small event trace. A correct final total alone can hide two wrong awards that happened to cancel each other.

What was checked

Local fixtures exercised valid native hits, one-hit rejection, cosmetic reactions and separate session scores. Internet-delay fairness and simultaneous real-peer shooting are separate tests, not proven by a local fixture. The examples describe the local Windows demo setup.
