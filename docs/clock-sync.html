Clocks, latency & round timing

Keep event time, receipt time and render time on explicit clock bases.

1. Name every time value

ValueMeaning
Local event timeWhen the sender observed the action on its clock.
Receipt timeWhen this peer received it.
Host-aligned timeAn estimated conversion into the authoritative round clock.
Render timeThe earlier time sampled by an interpolation buffer.
Wall-clock file timeUseful for logs/backups, not automatically comparable to world seconds.

Do not subtract os.time from GetRealTimeSeconds or compare two worlds’ elapsed seconds without a conversion. A world clock can restart during travel while a process/network session continues.

2. Exchange timestamp echoes

The local clock code sends a timestamp, echoes a remote one and records how long the echo was held. It uses bounded recent requests to estimate round trip and offset. This is a mod-level time estimate, not a Steam guarantee.

local rtt = receivedNow - originallySentAt - heldByPeer
if rtt < 0 then return nil end
local estimatedOffset = remoteStamp + rtt / 2 - receivedNow

The half-round-trip assumption does not reveal actual one-way delay on an asymmetric connection. Reject impossible or stale echoes and keep the uncertainty in mind when using the estimate for gameplay decisions.

3. Track estimate quality

Require enough recent accepted samples before treating a conversion as usable. Record age, round-trip estimate and rejected samples. A single fortunate packet is not a stable clock synchronisation result.

Do not let arbitrary remote timestamps create unbounded offsets. Validate sample ranges and define how the estimate resets or ages out after a pause, reconnect or world transition.

4. Define the scoring deadline policy

Choose whether eligibility is based on host receipt time, a validated host-aligned event time or another explicit rule. Host receipt time is simple but disadvantages delayed guest hits near the deadline. A grace period needs bounded timestamps and a settling phase, not an open invitation to submit late scores.

Preserve round ID and shot identity with the event. A correctly converted timestamp still belongs to the wrong round if its generation is stale.

5. Keep presentation smoothing separate

The interpolation buffer’s render delay should not silently become extra competitive time. The displayed remote player can be intentionally behind the authoritative event stream. Explain countdown/results using the shared accepted state, not the last rendered pose timestamp.

A countdown shown locally before both peers are synchronised is a presentation error even if the host’s internal timer is correct. Tie readiness to the state your challenge actually requires.

Timing acceptance cases

  • A valid timestamp echo updates the estimate.
  • A stale/malformed/negative sample is rejected.
  • Travel and reconnect reset the correct histories.
  • A guest hit near the deadline follows the documented rule.
  • A settling window closes and cannot reopen from an old packet.
  • The result is checked on real peers, not inferred from a local simulation.
