Attachments & rails

Separate the attachment list, the mounting point and the part fitted to it.

The attachment flow

The workbench creates Attach_POI_C widgets for attachment points. A point references its AttachPoint component, the current weapon and a popup list. Compatibility lookup decides which attachment classes that list can offer.

Entry pointObserved role
GetCompatibleMountsRecursiveResolve compatible mount definitions.
OnGetUserMenuContentBuild the attachment popup.
SetupAttachmentApply a class or remove a fitted part.
AttachPoint.ChildActorThe actor currently fitted at that point.

Nested rails

A rail can add mounting points of its own. A grip fitted to the rail is a descendant of that rail, not necessarily a direct child of the base weapon. Removing a parent can invalidate the child actor and its UI at the same time.

When iterating points during a clear operation, reacquire the current point list after each change. Don’t keep using an old list after the workbench rebuilds it.

Fit and remove through the game

For a valid live attachment-point widget, the native action takes a class reference to fit a part. Passing nil removed it in local tests:

-- Context: poi is a valid live Attach_POI widget.
-- This changes the assembly; it is not an inspection call.
poi:SetupAttachment(nil)

Let the game handle default-part behaviour and its refresh chain. Directly destroying a child actor bypasses that UI action and may leave the template or derived stats out of date.

Compatibility isn’t ownership

A part can be mount-compatible but not bought. A shop entry can be visible but locked. A saved assembly may contain a part that a purchased-set-only check misses. Keep these questions separate; see Ownership & unlocks.

Test repeated edits

Record stats before fitting, after fitting and after removal. Repeat with the same rail, then try removing the rail while a child part is still mounted. Check that a cancelled operation doesn’t remove a part from a newly selected gun.

For a stat report, keep the exact weapon, rail and child class names. A vague “negative stat” report is not enough to decide whether an extra subtraction occurred.

Walkthrough: trace a fit/remove action

1. Identify the point

Open the attachment editor and pick a point whose current part you can name. Record the POI widget, AttachPoint component and ChildActor before doing anything. If it is a rail’s own point, also record the rail actor that owns that branch.

Several points can offer the same part classes. The class of an attachment does not uniquely identify the point the player selected.

2. Record what the list means

Observe the menu before filtering or pagination. Count real attachment entries separately from the empty-slot icon and any tab row your mod adds. Decide whether your feature changes compatibility, ownership visibility or just presentation. Those changes should not be mixed into one undocumented “filter”.

For tabbed lists, partition the original item list, then add your navigation controls outside that item count. Otherwise reopening or rebuilding the list can accidentally count your own tab bar as another attachment.

3. Fit one known-compatible part

Use the normal click action first and confirm the visible child, the refreshed point list and a stat snapshot. If that action fails without your mod, investigate the base setup before expanding compatibility.

A mutating Lua action should use the intended game path and verified class type. Passing an object instance where a class reference is expected is not the same operation.

4. Remove and reacquire

After removal, do not use a cached child actor to ask what is now mounted. Reacquire ChildActor from the current AttachPoint. If the editor rebuilt its POIs, reacquire the point list too.

For a clear-all action, finish one removal, let the normal refresh chain run and inspect the new list before the next step. Protect the job against duplicate clicks, changed weapon, closed editor and world travel.

5. Test parent removal separately

Removing an empty rail and removing a rail with several children are different cases. Observe what happens to each descendant, its stats and its menu points. If the UI rebuild invalidates a child point, the job must skip that old reference rather than force another removal on it.

Pagination boundaries

Use ordinary Lua item arrays for your page calculation. For a positive page size, an item’s page is floor((index − 1) / pageSize) + 1. The number of non-empty pages is ceil(itemCount / pageSize). Decide whether an empty list shows no tabs or a single empty page, then test that policy explicitly.

Completion check

Verify fitting, removing, replacing, parent-rail removal, empty clearing and cancelled clearing. For expanded combinations, test handling and persistence independently. Report a stable list and working tabs as those specific results; they do not prove every offered combination is physically or mechanically valid.

What was checked

Single native removals, synthetic three-point clear batches and rebuilding/cancellation guards passed local fixtures. These do not prove every real fitted assembly saves and reloads correctly.
