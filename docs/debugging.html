Debugging

Start with the log and a repeatable set of steps.

Read the log

In the layout used here, the loader log is Ballistic/Binaries/Win64/ue4ss/UE4SS.log. Check its timestamp and search for your mod’s prefix.

Log when your script loads, when a hook installs and when the relevant callback runs. Those are three different checks.

local function log(message)
    print("[MyFirstMod] " .. tostring(message) .. "\n")
end

log("Script loaded.")

Handle Lua errors

A protected call can log a Lua failure and stop that operation:

local ok, err = pcall(function()
    -- Run one operation you are investigating here.
end)

if not ok then
    print("[MyFirstMod] " .. tostring(err) .. "\n")
end

pcall does not make an invalid native pointer safe. If the process crashes inside the engine or loader, simplify the callback and inspect the native stack.

Reproduce a problem

  1. Write down the game build, loader version and mod version.
  2. Use a minimal setup with the mods needed for the test.
  3. Record the exact weapon, part or menu involved.
  4. Compare the result before and after the operation.
  5. Restart fully, then repeat the same steps.

For a stat problem, record the value before fitting a part, after fitting it, and after removing it. “It went negative” doesn’t show whether the value dropped below its original baseline.

After a game update

Check function paths and signatures again. Confirm asset availability, menu construction and save behaviour separately. A successful startup log only proves that startup completed.

Walkthrough: locate the first broken layer

1. Is the code you edited actually loaded?

Add a unique startup version message, fully restart, and check the log timestamp. If an old version still appears, identify the installed copy before editing more files. A source folder and a packaged archive can both exist without either being the one the loader runs.

2. Does the relevant callback run?

Log the first call, the context’s full name and a counter. If there are zero calls, inspect the path, class loading and the real UI flow. If there are too many calls, inspect nested recursion and construction/refresh events. Rate-limit repeated diagnostics after the first few samples.

3. Is the data what you think it is?

Log the Lua type, reflected field type and an ordinary copied value. A non-nil wrapper is not automatically a loaded UObject. A property returning a placeholder is not automatically a callable function. Distinguish unavailable from a real zero, false or empty result.

4. Does the smallest native action work?

Use a disposable fixture if the action can change an assembly or save. Call one known function with one known compatible argument. Confirm the actual engine state afterwards. A successful pcall means no Lua error was reported; it does not establish the visible result or absence of a later native crash.

5. Does the UI reflect the result?

Check the model, label or menu after the action and after closing/reopening it. If the engine state changed but the display did not, investigate the refresh path. Avoid rewriting the state a second time simply because the first redraw was delayed.

6. Does the result survive the intended lifecycle?

Travel, return, restart and load a disposable save only when persistence is part of the feature. If the behaviour works until travel, focus on stale references and world resets. If it fails only after restart, focus on the persisted representation and reconstruction path.

Reading a Lua traceback

Start with the first error message and the file/line where your code failed. Follow the call stack outward to learn which callback entered it. A later cleanup error may be secondary; keep the original failure visible rather than replacing it with another generic message.

Use xpcall with debug.traceback when a small diagnostic operation needs a complete Lua stack. Do not wrap an entire feature in a silent pcall and continue as though it succeeded.

local ok, result = xpcall(function()
    return inspectCurrentContext()
end, debug.traceback)

if not ok then
    print("[MyMod] Inspection failed: " .. tostring(result) .. "\n")
    return
end

Reading a native crash report

Keep the exception address, module names and the last relevant fresh log lines. A UE4SS frame in a stack identifies where execution passed, not automatically which mod caused the invalid state. Compare a loader-only run, a minimal feature run and the exact reproduction.

If the fault only appears after several menu rebuilds, test object lifetime and delegate ownership. If it appears during container membership checks, check reference representation and the binding’s expected types. Do not “fix” a native fault by adding a Lua error handler that cannot intercept it.

A good final report

State the smallest reproduction, observed values, versions, test method and remaining uncertainty. Attach a relevant excerpt rather than a complete private save or an enormous log. The testing walkthrough provides a template and an acceptance matrix.
