Chat, names & text validation

Bound user text, preserve valid UTF-8 and separate display names from trusted identities.

1. Define text policy

Decide whether chat is single-line, how many bytes a message may contain, how names are displayed and which characters your actual widget treats as markup. A plain TextBlock and a rich-text renderer can require different handling.

Treat the display name as presentation. The connection/session identity decides ownership and permissions; a guest renaming themselves “Host” should not change authority.

2. Validate type, encoding and length

local function cleanLine(value, limit)
    if type(value) ~= "string" then return nil, "not text" end
    if not utf8.len(value) then return nil, "invalid UTF-8" end
    local text = value:gsub("[%c<>]", " "):gsub("%s+", " ")
    text = text:match("^%s*(.-)%s*$")
    text = text:sub(1, limit)
    while #text > 0 and not utf8.len(text) do text = text:sub(1, -2) end
    if text == "" then return nil, "empty" end
    return text
end

Lua string length counts bytes. Truncating in the middle of a multi-byte character can create invalid UTF-8, so trim to a valid boundary after applying a byte cap. This example strips angle/control characters for a simple display policy; it is not a universal HTML or rich-text sanitizer.

3. Give messages identities

A chat message is a one-time event. Include an event ID and stream/session identity, keep pending messages until acknowledged, and display a retry only once. A new snapshot sequence is not by itself the identity of a particular message.

Bind acknowledgement to the correct peer generation. Otherwise an old acknowledgement can retire a new stream’s messages, or reconnect can replay old history as new unread text.

4. Bound queue, history and send rate

Choose maximum pending messages, local history and a send interval. The local implementation has such caps and a visible “waiting for your friend” path. Those are usability and backpressure rules, not proof every delivery succeeded.

Muted display should not break protocol acknowledgement if the message was accepted. Otherwise a peer can keep retransmitting a message just because the recipient hid its presentation.

5. Integrate with input and notices

Focus the text field deliberately, prevent send keys from triggering unrelated gameplay actions, and restore cursor/input state when chat closes. Keep system notices distinct from player messages so a player cannot impersonate a trusted status just through its text.

For an unread counter, decide whether messages arriving while chat is visible count as unread. Reset on the intended user action rather than on every UI rebuild.

Text test cases

  • Empty, whitespace-only, long ASCII and long multi-byte messages.
  • Control characters and markup-like strings.
  • Duplicate delivery and lost acknowledgement.
  • Mute/unmute while messages arrive.
  • Reconnect with a new stream generation.
  • Typing, sending, Escape and reopening without stolen game input.

Use synthetic text in public examples, not private chat logs. See Input, focus & cursors for the menu side.
