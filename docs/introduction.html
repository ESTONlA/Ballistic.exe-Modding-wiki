Introduction

A practical guide to modding Ballistic.exe with UE4SS and Lua.

This wiki covers setting up your mod folder, finding game objects, hooking functions and troubleshooting scripts. Start with a small change, check it in-game, and build from there.

You don’t need Unreal Editor for the Lua examples here. UE4SS loads your scripts alongside the game and lets them interact with objects and functions that Unreal exposes at runtime.

Before you start

The examples come from the Windows demo. Game updates can change class names, functions and file layouts. Keep a backup of your saves and check your own build’s log when something behaves differently.

What can you do with Lua?

Lua mods can inspect loaded objects, call reflected functions, respond to game events and create UI using assets the game already contains. Some changes need only a few lines of code.

  • Adjust workshop behaviour and add controls to existing menus.
  • Read weapon or target information for tools and overlays.
  • Spawn and arrange existing assets at runtime.
  • Add keybinds, diagnostics and small quality-of-life changes.

These are starting points, not a guarantee that every game system is accessible. See Custom content for the limits of a Lua-only mod.

A small example

A mod begins with Scripts/main.lua. This is enough to check that the loader is running your file:

print("[MyFirstMod] Hello from Ballistic!\n")

The message appears in ue4ss/UE4SS.log after you launch the game. The first mod guide shows the complete folder structure.

Choose a learning path

You can follow the wiki in order, but you do not need to understand every game system before writing a small mod. Pick the path that matches the change you want to make, and stop at a result you can actually verify.

I have not written a Lua mod

  1. Install the loader and confirm a fresh log.
  2. Run a single startup message before calling any game function.
  3. Work through Lua basics until tables, callbacks and nil checks make sense.
  4. Split the mod into modules only once the single-file version works.
  5. Build the read-only weapon inspector and compare its snapshots.

Your first milestone is not an elaborate menu. It is a script that you can install, identify in a log, trigger once and disable cleanly.

I want to change a weapon or attachment

Read Weapon assemblies before editing a mesh or part. Then follow Attachments & rails and Weapon stats. The workflow is: identify the actual live gun, record a baseline, use one normal attachment action, inspect the changed branch and verify the result after leaving the menu. Save/reload is a separate milestone.

I want to add a menu control

Start with Finding game objects and Workshop UI. Learn which widget owns the canvas and how it is rebuilt. Create a visible but inactive control first, confirm its placement, then connect exactly one action. Test closing the menu while that action is pending.

I want targets, scoring or a range feature

Follow target discovery, hit attribution and range travel. Keep a cosmetic scene, a scoring mode and a cooked map as separate goals. A new card and a row name do not produce a new map package.

Read an example’s context before copying it

A block labelled “inside the callback above” is a fragment, not a complete main.lua. A block marked “pure Lua” does not need a live Unreal object. A block marked “mutating” changes state and should not be used as a discovery probe.

When a result is shown as <raw numeric value>, it describes an output format rather than a captured measurement. Exact numeric expectations appear only where a specific recorded fixture supports them. Evidence levels explain the difference.

When you get stuck

Reduce the problem to the last result you could prove. Did the file load? Was the class loaded? Did the callback run? Was it the active instance? Did the normal game action complete? Those are different questions. Use Debugging to work through them instead of adding more code around an unknown failure.
