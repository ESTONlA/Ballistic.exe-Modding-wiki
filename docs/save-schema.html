Save fields & runtime mirrors

Compare persisted fields with runtime mirrors without treating a reflected class as a complete save-file specification.

What the schema can tell you

The names below are recorded in the local object snapshot dated 10 October 2026. That snapshot does not identify its game build. Resolve the same names in your current build before using them; the investigation steps below are not a report that every operation was tested.

BallisticSaveGame_C declares persisted-looking properties, but a reflection dump does not describe the whole binary file format, property serialization flags, custom serialization, load order or migration rules. The useful starting point is a field inventory and a comparison with the live game instance. The current snapshot has both similarly named and differently named mirrors; never match them only by position.

A name match is only a candidate relationship. Confirm the direction and timing by observing normal game operations and the corresponding UpdateSave or RetrieveSaveInfo paths.

Compare without writing

  1. Back up the game’s save files while the game is closed. Record the file hash before the experiment.
  2. Record the game build and loader version separately from the old schema snapshot.
  3. Observe the loaded save object and current game instance after a normal load. Copy a small, explicit field set into plain diagnostic records.
  4. Perform one normal action such as buying one item or changing a display-unit setting.
  5. Compare runtime state immediately, then after the game’s normal save action and a clean reload.
  6. Hash the actual file again and explain which normal action was expected to change it. A changed hash alone cannot identify the field that changed.

Why bulk host-save copying is difficult

Replacing a guest’s progress is a product decision as well as a serialization task. Weapon templates, equipped loadout, owned parts, current ammunition, settings and completed progression have different scopes. A session-only host snapshot can be safer than overwriting a guest’s personal save, but it still needs type-aware construction and restoration. A plain table assigned to a reflected set or soft-class container is not a migration strategy.

Document a field relationship

  • Name both exact reflected properties and their recorded types.
  • Record which normal action changed each value and when.
  • State whether the result survived a clean reload.
  • List unrelated fields you deliberately did not copy.
  • Keep an unresolved ownership rule labelled unresolved.
