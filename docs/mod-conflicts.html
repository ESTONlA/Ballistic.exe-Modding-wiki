Finding conflicts between mods

Find which mods overwrite the same state and make your own changes cooperate with other tools.

Write a narrow reproduction first

Record the map, menu, selected gun/attachment and exact action that fails. Keep the game build, loader version and enabled-mod list with the report. A claim such as the laser changes back after 250 milliseconds is much more useful than the colours are broken, because it points toward a repeated writer.

Isolate with controlled enablement

  1. Confirm the behaviour with the game and loader before enabling the suspected feature.
  2. Test your mod alone in the same game state.
  3. Enable other mods in small groups and repeat the exact action.
  4. When a group causes the problem, split it until you identify the interacting pair.
  5. Repeat with the pair in the same configuration and record which state each mod writes.
  6. Restore the user’s original enabled-mod setup after the diagnostic.

Look for competing ownership

Shared stateTypical conflict
Laser MID parameterTwo enabled colour variants keep overwriting LaserColor.
Workbench childrenTwo mods clear/rebuild the same panel and delete each other’s buttons.
Input modeClosing one menu restores gameplay input while another menu is still open.
Weapon aggregate statsOne hook changes parts while another repeatedly rebuilds totals.
Camera FOVA global timer overwrites a mode-specific aiming or scope value.
Save collectionsDifferent mods assume incompatible ownership/progression meanings.

Prefer scoped changes

Change the smallest state that belongs to your feature. Use one per-component material instance, a dedicated child panel, a unique widget name and an explicit input owner. Keep an allowlist of the fields your mod writes. Do not treat pcall as a way to make broad native-container mutations safe: it cannot catch every access violation.

Report repeated replacement

If a material or widget changes after your own successful update, record the new object name and when it changed. Use a bounded diagnostic counter and a single clear warning rather than printing every tick. Back off or disable the feature if the ownership assumption is no longer valid. For a colour mod, one installed version is clearer than an invisible priority battle between four timers.

-- Pure Lua: warn once per observed conflict category.
local warned = {}
local function warnOnce(key, message)
    if warned[key] then return end
    warned[key] = true
    print('[MyMod] ' .. message .. '\n')
end

Include the useful evidence

  • Minimal enabled-mod pair and exact settings.
  • Before/after object identities and the state being overwritten.
  • Whether load order changes the result.
  • Whether restarting the game restores the expected baseline.
  • A concrete ownership rule or compatibility option, rather than an unexplained global override.
