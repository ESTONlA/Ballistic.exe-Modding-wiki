Spawning & actor ownership

Create disposable actors deliberately and clean up only what your feature owns.

1. Define what the actor represents

Decide whether the new object is a cosmetic proxy, an interactive target, a physics prop or scenery. Those choices affect collision, replication, ownership and cleanup. A mesh actor with collision disabled can be useful for a tracer but is not a playable target.

Start with one object. Record its intended world, class, transform and lifetime before spawning many copies. A successful SpawnActor result does not establish that the mesh, material and behaviour are all configured.

2. Acquire the current world and class

-- Context: current world and position were validated on the game thread.
local class = StaticFindObject("/Script/Engine.StaticMeshActor")
if not class or not class:IsValid() then return end
local actor = world:SpawnActor(class, position,
    {Pitch = 0, Yaw = 0, Roll = 0})
if not actor or not actor:IsValid() then return end

owned[#owned + 1] = actor
-- Configure only after the actor has been tracked for cleanup.

Keep the owning list reachable for the feature’s lifetime. Track the object immediately so a later Lua error while assigning a mesh does not leave an untracked actor behind. The surrounding action should clean up partial construction before reporting failure.

3. Configure one property group at a time

For scenery or a visual proxy, inspect mobility, component mesh assignment, scale, material, collision and replication deliberately. Some assignments require a movable component or a particular actor class. Confirm the actual result instead of assuming every setter succeeded.

Use a verified component reference such as the static-mesh actor’s StaticMeshComponent in the tested build. Do not invent an unreflected getter because the C++ engine has a similarly named method.

4. Keep engine ownership distinct from your bookkeeping

The engine actor’s owner/outer/attachment relationships and your Lua owned list serve different purposes. Your list says which objects the feature is responsible for cleaning up. It does not itself attach a component, assign network authority or make a pointer safe after travel.

When building an assembly, keep the parent/child relationship explicit and test what destroying a parent does to descendants. Don’t attempt to destroy every descendant twice through stale references.

5. Clean up on close, replacement and travel

Remove replaced proxies before losing their handles. On feature close, destroy the valid actors you created in that world. On world change, retire the old registry; don’t reach into a new world and perform a broad class-based deletion to simulate cleanup.

If you modify an existing game actor instead of spawning one, save the specific original state you intend to restore. Destroying that actor is not an appropriate general teardown for a borrowed object.

Acceptance checks

  • One actor appears at the intended transform.
  • A configuration failure removes the partially created actor.
  • Repeating setup does not duplicate the object.
  • Replacing a mesh/proxy does not leak the previous actor.
  • Closing and travelling retire the correct objects.
  • No unrelated game actor is deleted.

The local effects/proxy code used owned lists and per-world cleanup. This documents that pattern, not a guarantee every arbitrary spawned class supports the same setup sequence.
