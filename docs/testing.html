Test a mod step by step

Prove the smallest claim first, then test the actual player workflow.

1. Write a concrete claim

“Works” is too broad to test. Use a trigger and an observable result: “Removing the foregrip restores the installed-ergo baseline,” or “Closing the attachment editor hides the added button.”

Write the expected result before changing the code. For a stat issue, a negative final value is not enough; compare it with the same assembly’s starting value.

Use exact class or display names where possible. Save a fresh log after reproducing, not a file from last week. Remove personal paths and network IDs before posting it publicly.

3. Check pure Lua logic

Configuration validation, pagination boundaries, score deduplication and packet parsing can often be tested without Unreal objects. Give them ordinary values and assert the returned result.

local seen = {}
local function accept(id)
    if seen[id] then return false end
    seen[id] = true
    return true
end

assert(accept("round1:shot1") == true)
assert(accept("round1:shot1") == false)
assert(accept("round1:shot2") == true)

A mock can establish that your callback releases a busy flag after a Lua error. It cannot establish that an engine object is safe to dereference. State the distinction in the result.

4. Use native fixtures for engine behaviour

A native fixture uses actual engine objects with controlled ownership. For a child-actor removal test, create a disposable component and point the test widget at it rather than touching the player’s saved gun.

Keep a list of every actor, widget, hook and temporary file the fixture owns. Clean those up on success and on Lua failure. Do not stop an unrelated game process or alter another mod’s configuration as an unrecorded side effect.

5. Test the actual workflow

  1. Open the normal menu the player uses.
  2. Trigger the action through its real input path.
  3. Repeat it after the UI rebuilds.
  4. Change the weapon or close the menu while work is pending.
  5. Travel and come back.
  6. For a persisted change, restart and load a disposable save.

A widget created by code can pass construction checks while still being off-screen or blocked by another panel. The real input path is a separate check.

6. Add a two-PC matrix

ScenarioCheck on both screens
Both fire at onceTwo distinct shot IDs and correct owner attribution.
Same target hitNo duplicate reward; consistent final target state.
Switch gunsCorrect model and handling state; no orphaned meshes.
Restart / repeated travelBoth arrive with usable loadouts and reset registries.
Disconnect near round endClear cancellation or recovery; no old result applied.
Save snapshotConsent, backup and successful reload on a disposable guest profile.

Use separate Steam accounts and real peers for this stage. Simulated packet delay is useful for repeatability, but it is not a replacement for an actual session.

7. Write the result narrowly

Record what ran, what passed, what failed and what the test did not cover. “Ten synthetic removals returned to baseline” is useful. “All attachment bugs fixed” does not follow from it.

Once the relevant checks pass, save the tested artifact and its checksum. Re-run checks when code or an unresolved concern justifies it; repeating the same successful simulation does not broaden its scope.
