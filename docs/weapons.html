Weapon assemblies

A visible gun is an assembly of actors and components, not necessarily one mesh.

Find the equipped weapon

In a range, the local pawn exposes EquippedWeapon. The workshop uses its own displayed weapon reference, so don’t expect the range pawn to identify the gun on the workbench.

local H = require("UEHelpers")

RegisterKeyBind(Key.F9, function()
    ExecuteInGameThread(function()
        local pc = H.GetPlayerController()
        if not pc or not pc:IsValid() then return end
        local pawn = pc:K2_GetPawn()
        if not pawn or not pawn:IsValid() then return end
        local gun = pawn.EquippedWeapon
        if not gun or not gun:IsValid() then return end

        print("[MyMod] Equipped: " .. gun:GetFullName() .. "\n")
    end)
end

Parts and components

Observed weapon classes include C_WeaponBase, C_WeaponPart and the Blueprint A_WeaponBase_C. Parts expose a ParentWeapon reference. ChildActorComponents can own attached part actors, which can have their own descendants.

Enumerate the assembly before changing it. A core barrel, a fitted rail and a nested foregrip can live at different depths. Reading just the root actor’s mesh misses much of the weapon.

local children = {}
gun:GetAllChildActors(children, true)
for i = 1, math.min(#children, 128) do
    local child = children[i]
    if child and child:IsValid() then
        print("[MyMod] Part: " .. child:GetFullName() .. "\n")
    end
end

Templates are different from live actors

CurrentWeaponTemplate records a selected assembly. A spawned weapon is the live actor built from it. Changing the visible actor alone does not establish that the saved template changed, and changing a template does not automatically refresh every existing actor.

The observed template has separate weapon-class, main-part, attachment and grip data. The generated field names have suffixes; inspect the current struct rather than copying offsets.

Visible doesn’t mean usable

A mesh proxy can show another player’s gun without implementing its firing mechanism. A usable gun also needs the correct actor class, parts, ammunition, ownership and input path.

Test local use separately from remote appearance. Likewise, hiding a source gun and drawing a replacement mesh does not make a new inventory weapon.

Test an assembly

  1. Record the selected template and visible part tree.
  2. Change one part and confirm only the expected branch changes.
  3. Leave the workbench and test handling and firing.
  4. Travel to a range and back.
  5. Restart and check the saved assembly separately.

Walkthrough: inspect one complete assembly

1. Prepare a known gun

Use a gun and normal part combination you can identify in the game. Record the selected base weapon, core parts, fitted attachments and currently gripped part. Keep a screenshot of the workbench view so a later actor list has a visual reference.

Do not begin with an already complicated cross-weapon assembly. A shorter part tree makes it easier to identify which object was added by one operation.

2. Find the live gun for this context

In a range, read the local pawn’s EquippedWeapon. In the attachment editor, inspect the editor’s CurrentWeapon. Log the world and full object name beside each snapshot. A class default object has defaults; it is not the gun the player is holding.

If the object is missing, report “not ready” and stop the sample. Creating a replacement weapon just to make inspection return something changes the question you were trying to answer.

3. Capture the tree, not just a count

List the root and descendant actors with a bounded output limit. For a deeper investigation, inspect each child’s owner/component relationship and any ParentWeapon reference. A flat list is enough to prove an actor exists, but it does not explain which rail owns a nested grip.

Keep copied names and selected numeric values as the baseline. Reacquire live actors for the next sample. Holding old references across a rebuild can turn a useful comparison tool into the source of the failure.

4. Change one ordinary part

Use the game’s normal UI to replace or remove one attachment. Capture a second snapshot after the action and compare the changed branch. Record which actors disappeared, which were recreated and whether the main gun identity stayed the same.

A recreated actor can have the same class but a different instance suffix. Compare class identity when asking “is this the same type of part?” and instance identity when asking “is this the same live object?”.

5. Separate visible, usable and saved state

StateHow to check it
Visible assemblyThe displayed geometry and captured child tree match.
Usable assemblyHandling, aiming, magazine interaction and firing work in the range.
Selected templateThe game’s selected loadout reconstructs the intended parts.
Persisted assemblyA restart and disposable-save reload reconstruct the intended parts.

Passing the first row does not establish the other three. This distinction is especially important for model proxies and Lua-only replacement previews.

Understanding relative transforms

A remote weapon display needs each visible mesh in a common local coordinate system. Copying world positions directly produces offsets that depend on where the source player stood. The local implementation captured mesh positions relative to a weapon-root transform, then rebuilt that relationship for the visual proxy.

A complete mesh capture also considers rotation, scale, deduplication and meshes on child actors. Verify the reconstructed assembly while moving, aiming and changing weapons; a correct static screenshot is only the first check.

Troubleshooting the result

If the root gun appears but attachments do not, inspect child-actor traversal and component selection. If the model appears late, inspect asset-loading and capture cadence. If it is offset or facing backwards, compare transform spaces before adding arbitrary constants. If the local usable gun disappears after travel, inspect loadout reconstruction separately from the friend’s cosmetic proxy.

What was checked

EquippedWeapon lookup and assembled mesh capture were used in local range fixtures. Arbitrary replacement weapons, imported models and every possible assembly are not verified. The examples describe the local Windows demo setup. See Checking game updates before using them on another build.
