Multiplayer architecture

Connecting two players is the beginning. Shared game state still needs explicit rules.

Connection isn’t replication

A Steam session or invitation identifies and connects peers. It does not automatically make every single-player actor, UI action, weapon part or score replicate.

The local multiplayer implementation combines a listen-server travel path with a native Steam bridge and custom state messages. That architecture is a mod implementation, not an official multiplayer API supplied by this wiki.

Separate state from events

Send as stateSend as events
Player pose, aim and equipped appearanceA shot, a hit or a chat message.
Target pose and current hit stateA round-start or recovery request.
Current round phase and scoresA one-time save offer or acceptance.

Snapshots can supersede older snapshots. One-time events need IDs, acknowledgement and duplicate handling. Replaying the same acknowledged hit must not award its points again.

Authority and validation

Choose who decides travel, target state and scoring. A host-authoritative mode should validate the sender, session, round, target identity and bounded event values before applying a guest request.

Never accept arbitrary asset paths, file paths or Lua source from a network message. Use explicit allowlists and fixed save slots where appropriate.

Movement and visible guns

Render remote movement from buffered snapshots rather than snapping directly to each packet. Reset the buffer for teleport or world changes. Interpolation hides normal packet gaps; it does not fix wrong authority or missing state.

Remote weapon appearance can be reconstructed from mesh references and relative transforms. Reuse unchanged meshes and clean up replaced ones. A cosmetic proxy is not another fully simulated gun actor.

Interruptions and testing

Give every session and world generation a distinct identity. Discard stale packets after reconnect or travel. Cancel active rounds when a player disconnects, and recover through an explicit ready/start flow.

Test on two PCs/accounts: simultaneous shots, the same target hit by both peers, gun switching, range restart, repeated travel and a disconnect near round end. A local simulated-peer test cannot establish real network behaviour under delay.

Step-by-step development order

1. Prove connection and identity

Use two PCs and separate accounts. Confirm who is host, who is guest and which session each belongs to. Log session identity and protocol version in diagnostics without exposing private IDs in public reports.

A successful invitation is a connection milestone. It does not prove that range travel, guns, targets or progression are shared.

2. Build a stable roster

Resolve current player states, controller/pawn links and display names. Rebuild those references after travel. Keep local/remote role distinct from list order so sorting the UI does not swap ownership.

3. Share appearance and pose

Send bounded state snapshots with sequence and session information. Buffer remote poses for interpolation, reject old generations and reset on teleport. Separate cosmetic pose cadence from reliable gameplay events.

A proxy model and nameplate can provide useful presence while the game’s real remote pawn has a different replication path. Document which object actually moves and which object is cosmetic.

4. Move both players through a known range

Have the host select an allowlisted destination, require the needed readiness, perform the correct shared travel operation and wait for both arrivals. Reacquire weapons and targets only in the new world. Verify both local usable guns and remote visible guns; either can be missing independently.

5. Add reliable gameplay events

Give shots, hits and round actions explicit IDs. Keep an acknowledgement/deduplication policy so a retry is safe. Bound the queue and define what happens when it is full rather than endlessly allocating memory or silently losing scoring events.

6. Make one accepted result authoritative

For a host-authoritative challenge, validate guest events against the current world/round and known target registry, then publish the accepted state. Cosmetic impact playback should not invoke the game’s reward path again.

Validate asset identifiers against a narrow known set. Never interpret a received string as arbitrary Lua, a filesystem path to overwrite or a map to travel to.

7. Handle interruption before adding more modes

Disconnect, reconnect, host travel and save transfer can interrupt a round. Retire old session/world generations, explain the cancellation, and clear stale pending actions. A reconnect should not replay last session’s hit queue into a new round.

8. Test the real peer path

Repeat simultaneous firing, same-target hits, gun switching, target motion, restart and several travel cycles. Add delay and loss experiments when possible, but keep them distinct from the actual internet session result. Two windows in one process or a simulated peer are not two independent clients.

Fields worth designing explicitly

FieldPurpose
Protocol versionReject incompatible packet formats.
Session / peer generationDiscard an old connection’s data.
World / travel generationAvoid applying a previous range’s objects.
Round IDKeep events attached to the correct challenge.
Sequence / acknowledgementOrder replaceable state and retire reliable events.
Event ID / target IDDeduplicate actions and resolve game entities without remote pointers.

Keep save sharing separate

Live gameplay replication and host-save snapshot transfer have different consent, integrity and recovery requirements. The save flow should pause conflicting travel/actions and require a separate apply confirmation. Do not make joining a lobby silently overwrite a guest’s progression.

Write a release claim that matches the test

“Both players connected and saw models” is a useful result. It is not evidence that both could fire simultaneously, score consistently under delay or restore saves after disconnect. Publish the supported scope and the checks performed, and keep unverified later scenarios distinct from earlier user-confirmed connection.
