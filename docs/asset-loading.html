Asset paths & loading

Distinguish a content reference, an installed package, a loaded object and a usable asset.

Four separate checks

CheckEvidence
ReferencedA row, thumbnail or object points at a name.
PresentThe appropriate package appears in the installed archive.
LoadedThe runtime request returns the expected valid object type.
UsableThe asset displays or behaves correctly in the intended world.

Do not collapse these into one “asset exists” flag. The custom-range work produced a card before a new playable destination; the model experiments loaded materials without establishing a correct held weapon. Those outcomes are useful precisely because their limits are separate.

1. Record the exact path and type

Keep the package/object path separate from its filename in an archive browser. A Blueprint class reference commonly ends with a generated class name, while a static mesh, material or sound has its own object name. Preserve case and suffixes from the actual reference.

/Engine/BasicShapes/Cube.Cube
/Game/VFX/MuzzleFlash/MuzzleFlash.MuzzleFlash
/Game/SFX/Cues/Shots/Shot_9mm.Shot_9mm

2. Load on the game thread

ExecuteInGameThread(function()
    local mesh = LoadAsset("/Engine/BasicShapes/Cube.Cube")
    if not mesh or not mesh:IsValid() then
        print("[MyMod] Cube asset unavailable.\n")
        return
    end
    print("[MyMod] Loaded " .. mesh:GetFullName() .. "\n")
end

LoadAsset belongs on the game thread in the API used here. StaticFindObject instead searches what is already loaded. Use a low-frequency discovery path and cache successful results; loading the same path every render tick is unnecessary work.

3. Validate the returned type

Before passing a result to SetStaticMesh, a material setter or a sound function, confirm it is the type that function expects. A valid UObject with a familiar name is not sufficient. The local audio code explicitly checked SoundBase compatibility before playback.

If the asset type or dependency is missing, report that specific result. Do not substitute an unrelated object and let the next native call become the first diagnostic.

4. Cache without hiding failures

Cache an asset after a successful load. If the first attempt happens before its context is ready, distinguish “retry later” from “known unsupported path”. Keep bounded retries and an explicit error state. A permanent false cache created during early startup can make a later valid asset look unavailable forever.

World-specific spawned actors are not the same as loaded content assets. Even when the asset remains loaded after travel, reacquire the current world and create new world-owned instances as needed.

5. Prove usability in one place first

Use one disposable mesh/effect in a safe location with known scale and material. Verify requested versus actual transform, visibility and cleanup. Only then build a large scene or proxy assembly. This makes a material/loading problem distinguishable from an offset or occlusion problem.

For new external content, continue to Meshes, materials & textures and Custom content. An FBX filename is not directly a cooked Unreal mesh reference.
