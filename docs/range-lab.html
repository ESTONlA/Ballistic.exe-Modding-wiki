Plan a runtime range

Plan and verify a runtime scene in stages before calling it a new map.

1. Choose the actual deliverable

A new range card, a runtime scene inside an existing world and a new cooked map are different deliverables. Decide which one the prototype is meant to produce. If it must be Lua-only, document that it reuses a host world and cooked assets instead of promising an independent cooked level.

The recorded apartment/river experiment made a custom card and runtime geometry, but did not establish a finished lighting/layout result. Use that as a lesson in staging, not a claim this chapter ships a completed apartment range.

2. Write a scene brief with measurable constraints

Host map:
Player firing position and direction:
Near / medium / far target distances:
Safe firing lane and sight lines:
Scenery and bridge / river placement:
Required cooked meshes and materials:
Collision and out-of-bounds policy:
Target classes and scoring policy:
Return / emergency recovery action:
Cleanup and travel behaviour:

A reference image can guide composition, but turn it into positions, dimensions and a player view to test. A screenshot of buildings somewhere in a pool is not the same composition as firing across a river beside a bridge.

3. Calibrate one object and the player view

Use a known mesh at a verified transform close enough to see. Log the player position, forward direction and requested/actual object position. Confirm scale, mobility and material before placing distant structures.

Choose a local scene origin so the plan is expressed relative to the firing position. Convert those local placements consistently using the chosen basis; do not mix world Y with the player’s current right direction.

4. Build a plan before spawning

local layout = {
    {id="near-target", forward=2500, right=-200, up=100},
    {id="far-target", forward=7000, right=600, up=150},
    {id="bridge-reference", forward=3500, right=1800, up=0}
}
-- These are example local-plan units, not a finished map or measured asset sizes.

Review the plan from the intended shooting view. Keep a clear lane and enough room for the player’s weapon/camera. Do not assume a spawned object beyond an indoor host map’s wall is visible just because its coordinates are correct.

5. Add one subsystem per stage

StageAcceptance result
GeometryThe reference object and layout appear in the intended view.
PresentationMaterials, sky/ambient response and exposure are readable.
CollisionThe spawn and firing lane are not blocked accidentally.
TargetsReal target actors are identifiable and respond through the intended path.
ScoringThe custom rule counts valid attributed events once.
LifecycleExit, restart, travel and cancellation retire only owned objects.

Keep a recovery path available while experimenting with placement. Teleporting the player into a detached scene should occur only after construction succeeds, not before a long failing spawn sequence.

6. Diagnose darkness with a fixed reference

Do not repeatedly change view distance when you already have visible dark geometry. Compare an unchanged object/material and the camera’s actual render context. Confirm which light/skylight/postprocess components were affected and record a visible before/after result.

An emissive fallback can prove placement but should be labelled diagnostic if the intended scene requires normal lighting. A bright gun does not by itself prove the remote apartment faces receive the same ambient environment.

7. Finish the teardown before increasing scale

Track all created actors and target registries. Test feature close, failed partial construction, repeated entry and travel. A large runtime scene that leaks hundreds of objects each visit is not a finished range even if the first entry looks good.

For shared travel, wait for both peer worlds/loadouts/targets to be ready. For an actual new cooked map, follow a separately verified asset pipeline; this runtime plan does not reconstruct the developer’s Unreal project.
