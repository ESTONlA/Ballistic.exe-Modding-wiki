Diagnosing weapon failures

Follow a failed shot from the game notification back to the mechanical state that caused it.

What is actually exposed

The names below are recorded in the local object snapshot dated 10 October 2026. That snapshot does not identify its game build. Resolve the same names in your current build before using them; the investigation steps below are not a report that every operation was tested.

A failure notice is a useful observation point. It is not a command to clear a jam, and receiving a notice does not establish that a projectile was created. The native weapon class declares notification methods, while the failure enum records distinct reasons such as safety on, unloaded, hammer not cocked and bolt held open. Keep those reasons separate in logs.

C_WeaponBase reference

Start with the normal failure

  1. Disable your proposed fix and select a gun whose normal controls you understand. Record its complete attachment and ammunition setup.
  2. Try a known blocked action once, such as attempting to fire with the safety engaged. Write down the visible message without changing anything in the save.
  3. Find the live weapon actor and the relevant notification UFunction. Confirm whether the function is native or Blueprint before choosing hook phase.
  4. Capture the failure enum and a timestamp into ordinary Lua values. Defer formatting and UI work until after the callback.
  5. Repeat with the action allowed. A successful shot should not be classified as the same blocked attempt.

Notification entry points

Function / eventWhat to check before using it
NotifyWeaponFailureInspect its recorded fields and hook timing; do not pass a guessed enum argument.
NotifyMalfunctionCompare the event with the visible HUD notice. A second notification may describe the same attempt.
ProcessBulletFiredUse the shot path as a separate observation; a trigger press is not equivalent.

The exact numeric failure values are in the enum reference. Preserve the source spelling EWeaponFailureTypes. Ignore WF_MAX as a gameplay value.

Build a failure timeline

Give each local trigger attempt an observation ID. Log the active weapon identity, recent manipulation state, failure notice and any later fired-projectile event. Start with a single gun and a generous correlation window, then measure how far apart real callbacks arrive. Do not group every event in one rendered frame into one shot: automatic actions and multiple projectiles can share a frame.

ObservationInterpretation to investigate
Failure, no projectileThe action was blocked or ignition stopped before firing.
Projectile, then failureA later operation such as cycling may have failed; inspect ordering.
Two notices, one attemptCheck native/Blueprint forwarding and duplicate observers.
No notice and no projectileYour observer may be attached to the wrong gun or function.

Why not just clear every flag?

The bolt, hammer, firing pin, magazine and cartridge form a state machine. Forcing a visually closed bolt or replacing the displayed error text may leave the cartridge owner, chamber reference or held-open state inconsistent. First build a read-only overlay that explains the failure. A mechanical change should go through the same validated action the player uses and should have a test for a second attempt, ejection and reload.

Check the observer

  • Observe at least three different blocked states without crashing or creating ammunition.
  • A normal shot is logged once even when both Blueprint and native events are visible.
  • Switching guns does not leave the previous actor attached to the observer.
  • Removing the diagnostic returns to the original behaviour; no save conversion is involved.
