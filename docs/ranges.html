Range menus & travel

A range card is UI data. A playable destination also needs a cooked map and a working travel path.

Range menu data

The range table is /Game/Data/Ranges/RangeData.RangeData. The PistolRange row mapped to Range_SwimmingPool in local checks. Its display label is Azure Swimming Pool.

The inspected table also had rows such as Valley and ShoppingMall. Their presence did not prove those maps were usable in the demo.

What makes a card appear?

Two observed UI entry points are RangeList.PreConstruct and RangeListItem.SetSelected. The menu also checks the game instance’s UnlockedRanges, so adding a row alone may leave the card absent.

A runtime-only custom card was made visible locally by adding its row name to the in-memory unlocked list. That was an experimental menu change, not a demonstrated permanent unlock or newly cooked map.

Local and shared travel

Opening a map for one local player is different from moving a connected listen-server session. The local multiplayer code used the AdvancedSessions ServerTravel path with bUseSeamlessTravel enabled and a ?listen destination.

That solution depends on the session and driver already being valid. Appending ?listen to an arbitrary OpenLevel call is not a complete multiplayer implementation.

After arrival

  1. Confirm the actual current level name and world identity.
  2. Reacquire controllers, pawns, weapons, targets and UI.
  3. Confirm the local player has a usable weapon and ammunition.
  4. For multiplayer, confirm both peers arrived before starting a round.
  5. Try restart, return to bunker and repeat travel.

Building a detached scene by teleporting within the pool world still uses that world’s lighting and lifecycle. See Custom content.

Walkthrough: investigate a custom range entry

1. Verify the normal selection flow

Start without the custom entry and follow the actual Enter Range and confirmation flow. Record which screen constructs the list and what selecting a working range does. A confirmation screen is not itself the range list; hooking the wrong stage can miss the actual widgets.

2. Inspect one working row

Read the known PistolRange row and its map field. Record the display label, row name, destination ID and verified package separately. Do not use the display label as a package path.

3. Separate visibility from selection

If an added row is absent, inspect the list’s unlock check and row iteration. If it appears but cannot be selected, inspect the card’s selection state and callback. If it is selected but travel fails, inspect the destination and travel call.

During the recorded runtime-card work, bounded numeric iteration avoided an out-of-bounds iterator freeze. That was a container-binding failure, not a reason to keep enlarging or recolouring the card.

4. Confirm the destination by entering it

Check the actual current level after travel. A card can have the desired title and still route to the swimming pool. That is a successful card prototype, not a new playable map.

An unavailable destination returning to the main menu should be recorded as a failed travel result. Don’t keep advertising the destination solely because its table row exists.

5. If building a runtime scene, prove placement first

Spawn one known mesh in a clearly visible position relative to the player and log the requested and actual transform. Confirm mobility permits the intended operation. Expand the layout gradually, with a safe spawn and an escape/return route.

Placing buildings far beyond an indoor pool’s walls can produce a successful spawn log and nothing visible. The requested coordinates, player facing, source-target distance and occlusion all matter.

6. Test presentation independently

Verify sky, ambient light, materials, exposure and shadowing in the host world. If the player’s gun is bright but distant runtime structures are dark silhouettes, that is useful evidence against a simple “everything was culled” explanation. Inspect the render context before trying another arbitrary view-distance value.

A shared range-arrival handshake

For multiplayer, distinguish request, countdown, travel, arrival, object rebuild and ready-to-play phases. The host should not start a round merely because its own loading screen finished. Confirm the guest’s world generation and relevant target/loadout state too.

On failure, expose a recovery action such as retry, restart or return to bunker. A hidden retry loop that repeatedly travels both peers can turn one bad destination into a confusing session failure.

Verification sequence

Test normal entry, custom-card selection, arrival identity, spawn safety, visible targets, usable guns, exit, restart and repeated travel. For a true custom cooked map, document its package/loading pipeline separately from runtime geometry inside an existing map.

What was checked

Pool travel, restart and return were exercised in local native/listen fixtures. Two-PC travel reliability and absent demo maps are not implied by those checks. The examples describe the local Windows demo setup. See Checking game updates before using them on another build.
