Check your build

Use the loader’s object viewer or dump to confirm paths. Keep a small text record of the build, object name, signature and action you tested. See Debugging for a repeatable check.

Walkthrough: turn a path into a usable reference

1. Copy the full reflected name

A dump entry can include a type prefix, an object path and a member suffix. Preserve the exact case and spelling first. Only remove a type prefix where the lookup API expects the object/function name without it.

Do not copy a runtime address from an old dump into a script. Addresses belong to a particular process and can change after garbage collection, travel or a restart.

2. Separate class, object and package names

A map package such as /Game/Maps/Ranges/Range_SwimmingPool is not the same identifier as a generated widget class such as Attach_POI_C. A display label such as Azure Swimming Pool is not either of those paths. Keep fields named mapId, packagePath and displayName distinct in your own data structures.

3. Use context to select an instance

Load or locate a class, then find the live object used by the current menu or range. Record its world and full name. If the player switches weapons, the same class can produce a different instance; the feature needs the new instance.

4. Check the member’s signature

Before calling a function, read its input/out/return fields in the dump. Before writing a property, record its type and owner. A generated struct field with a long suffix should be copied as a complete identifier, not reconstructed from its display label.

Useful research sheets

Keep a small per-build sheet for each subsystem: exact class path, observed instance context, relevant functions, parameter types and one successful action. Link that sheet to the guide that explains behaviour; an unannotated catalog alone does not tell a modder what is safe to call.
