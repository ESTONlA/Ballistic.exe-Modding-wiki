Working with hooks

A hook runs your code when the game calls an Unreal function.

Find a function

Use the UE4SS object viewer or an object dump to locate the exact reflected function path. Class names and function names are case-sensitive. A Blueprint function often has a path like this:

/Game/UI/HUD/Workshop/BunkerHUDItems/Attach_POI.Attach_POI_C:GetCompatibleMountsRecursive

This path was observed in the demo’s attachment UI. It may not be loaded until workshop assets are present.

Wait for the function

Don’t assume a Blueprint is available when main.lua first runs. Check for it on the game thread, and register your hook once.

local path = "/Game/UI/HUD/Workshop/BunkerHUDItems/Attach_POI.Attach_POI_C:GetCompatibleMountsRecursive"
local installed = false

LoopAsync(2000, function()
    if installed then return end

    ExecuteInGameThread(function()
        if installed then return end
        local fn = StaticFindObject(path)
        if not fn or not fn:IsValid() then return end

        RegisterHook(path, function(context)
            local object = context:get()
            if not object or not object:IsValid() then return end
            print("[MyFirstMod] Workshop lookup called.\n")
        end)

        installed = true
        print("[MyFirstMod] Hook installed.\n")
    end)
end

Read parameters carefully

Hook arguments can be UE4SS parameter wrappers. Use the access pattern documented for the parameter’s type, and inspect the signature before reading or changing it. Callback phase and return-parameter behaviour can differ between native and Blueprint functions.

The sample above only reads the context and logs a call. It does not alter mount compatibility or attachments.

Avoid common mistakes

  • Don’t install the same hook on every timer tick.
  • Don’t call the hooked function from its own callback unless you have a deliberate recursion guard.
  • Don’t assume a path from an older game build is still correct.
  • Don’t use a Lua error handler as protection against native memory crashes.

Check the UE4SS API documentation for your loader version before writing to parameters or relying on pre/post callbacks.

Walkthrough: investigate one hook

1. Find the owner and full signature

Search the object dump for the function name, then read the owning class and parameter properties around it. Keep native paths beginning with /Script separate from Blueprint paths beginning with /Game. A similarly named function on a derived class can be a different integration point.

Record parameter order and types. A bool, object, struct, out array and return value require different handling. Don’t infer the whole signature from one callback that happened not to crash.

2. Wait for the function to exist

A cooked Blueprint can be present in the archive but absent from the current object registry. Trigger the normal menu or range that loads it, then retry StaticFindObject at a low frequency. Register once after the lookup is valid. Do not run LoadAsset repeatedly from a background callback just to force progress.

RegisterHook targets reflected UFunctions. The current API reference does not support delegate functions through that registration path; a widget delegate name is not automatically a hookable action.

3. Choose the correct callback phase

The current RegisterHook reference distinguishes native and Blueprint paths: the second argument is a pre callback for /Script functions and an after callback for other paths; an optional third argument supplies a native post callback. Match the docs to your installed loader rather than naming every second-argument callback a “pre hook”.

Start with a callback that logs and returns nothing. A hook return value can change a function’s result; accidentally returning a helper’s value can therefore change gameplay.

4. Read context before parameters

local function onCalled(context)
    local actor = context:get()
    if not actor or not actor:IsValid() then return end
    print("[MyMod] Called on " .. actor:GetFullName() .. "\n")
end

Confirm this runs on the expected instance. Only then add one parameter at a time. Copy numeric values or component coordinates into ordinary Lua tables if they need to outlive the callback; don’t assume a parameter wrapper remains a safe reference after the call finishes.

5. Keep the hook identifiers

local preId, postId = RegisterHook(path, onCalled)

local function removeMyHook()
    if preId == nil then return end
    UnregisterHook(path, preId, postId)
    preId, postId = nil, nil
end

Keep both returned IDs with the path. This is your hook’s identity; don’t try to unregister another feature’s callback by guessing its IDs. For a reload/reinitialisation path, remove the old registration before installing the replacement where supported.

Recursion and reentrancy

A hooked function can call related functions that eventually reach the same hook again. Calling it yourself from its callback can create direct recursion. Use a deliberate guard around the mutating operation, release it on Lua failure, and avoid treating every nested call as a separate user action.

For UI hooks, a function may run during both construction and refresh. Adding a button each time without checking its existing parent creates duplicates. The fix belongs in your construction lifecycle, not in an arbitrary delay.

When a UI return parameter is missing

In the recorded attachment popup test, the Blueprint post callback did not supply the return parameter expected by the first tab implementation. Reading the widget’s stored AttachmentsList property supplied the needed list instead. That is a specific observed workaround, not a universal rule that return parameters never work.

Dump the signature, log what the callback actually supplies and verify the resulting visible list. A registered hook with zero useful callbacks is not a completed feature.
