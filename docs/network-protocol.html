Messages & reliable events

Design bounded messages, revisions, acknowledgements and safe event retries.

1. Separate replaceable state from one-time events

A new pose can supersede an older pose. A shot, chat message or accepted hit must not be silently replaced by the next packet. Model those as different streams with different retry and deduplication rules.

The local implementation sends revisioned appearance/state plus acknowledged event streams. Sending everything every tick without identity can appear to work locally while duplicating rewards or losing gun changes under packet loss.

2. Define byte framing before decoding fields

Length-prefixed fields permit text to contain delimiter characters without guessing where a field ends. Count bytes consistently at both ends. Reject an invalid prefix, over-limit length, truncated body, forbidden bytes and unexpected trailing data before touching the engine.

local function decodeOneField(payload, limit)
    if type(payload) ~= "string" or #payload > limit + 6 then return nil end
    local colon = payload:find(":", 1, true)
    if not colon or colon > 6 then return nil end
    local digits = payload:sub(1, colon - 1)
    if not digits:match("^%d+$") then return nil end
    local count = tonumber(digits)
    if count > limit then return nil end
    local body = payload:sub(colon + 1)
    if #body ~= count or body:find("\0", 1, true) then return nil end
    return body
end

A real envelope also needs a version/magic value, the required field count and per-field validation. Do not accept extra fields quietly unless the protocol explicitly defines forward compatibility.

3. Distinguish sequence and content revision

A snapshot sequence orders snapshots. A gear revision identifies a changed weapon appearance. An acknowledgement says which content/event was accepted. Keeping those concepts separate lets unchanged large gear data stay out of routine pose packets while still retrying a lost gear update.

If sequence numbers wrap, define a bounded modular “newer” comparison. A simple numerical greater-than test stops working at the wrap boundary. Test duplicate, older and half-range ambiguous inputs explicitly.

4. Make event application idempotent

Give each event an ID within a session/round generation. Apply the next accepted event once, then acknowledge it. A repeated event should confirm the already accepted result without awarding points or playing effects again.

If an ordered event fails validation or application, decide whether the stream rejects/cancels or waits for recovery. Do not advance acknowledgement past work you did not apply, and do not let an invalid head event block the queue forever without a visible error policy.

5. Bound queues and values

Set maximum payload size, field sizes, pending events, history and retained generations. Validate numeric ranges, finite coordinates, allowed message kinds and known entity IDs. A decoded string is not yet an authorised gameplay action.

When backpressure occurs, show the user that the connection is catching up or reject the new action. Silently dropping a scored hit is not equivalent to dropping an obsolete cosmetic pose.

6. Validate the sender and context

Bind acknowledgements to the peer/session they belong to. A forged or stale acknowledgement must not retire unrelated pending events. Verify world/round generation and host/guest permissions before applying travel, target or score changes.

Use allowlisted cue/asset/destination IDs. Never turn a peer-supplied string into arbitrary Lua execution, an unrestricted file path or an unchecked engine object lookup.

Protocol test cases

  • Encode/decode valid boundary-sized fields.
  • Reject truncated, oversized, malformed and trailing data.
  • Retry an event after acknowledgement loss without applying it twice.
  • Drop stale session/world packets after reconnect/travel.
  • Preserve a large appearance revision across lost snapshots.
  • Recover or clearly stop when the reliable queue fills.
