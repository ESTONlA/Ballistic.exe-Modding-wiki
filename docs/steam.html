Steam sessions & invites

Understand sessions, invitations, transport and gameplay authority as separate layers.

1. Separate four layers

LayerWhat it establishes
Steam identity / inviteWho is being invited and how a join request is delivered.
Session / connectionWhich peers belong to the active lobby/driver.
TransportHow messages move between peers.
Gameplay protocolWhat a received message means and who may apply it.

Valve’s Steam Networking documentation describes messaging/sockets APIs and relay or direct connectivity where appropriate. That transport does not automatically implement your game’s target state, scoring, interpolation or save rules. Do not describe every session as gameplay running on a Valve-hosted game server.

2. Check the actual game/loader integration

The local project uses the game’s SteamSocketsNetDriver path together with a mod-owned native bridge. Its Lua code validates the available driver definition, remembers the previous configuration and has a restoration path. That is a particular implementation, not a universal one-line method for turning every Unreal game into multiplayer.

Before changing a driver definition, record the original value and confirm the expected reflected structure exists. A game update can change what is exposed. Don’t overwrite arbitrary networking settings merely because a class name appeared in another game’s guide.

3. Bind an invite to a valid join state

The local invite helper loads a matching native DLL from its mod-owned directory, checks a bounded status result and advertises joining only in the appropriate hosting state. The Lua and native pieces need compatible exports/versions.

An invite accepted while the host is no longer accepting players should fail or explain the new state cleanly. Old advertised join data must be cleared when hosting ends; otherwise a friend can enter a stale flow long after the UI says the session closed.

4. Preserve identifiers accurately

Keep Steam account identifiers as validated strings when passing them through formats that may not preserve all 64-bit integer values. Display names are not connection IDs. A syntax-shaped number alone also does not establish that the sender is an authorised member of the current session.

Bind connection, protocol version, peer identity and session generation together. Retire the previous generation on reconnect so a late packet cannot become a valid event for the new session.

5. Observe the connection you actually have

A relay-capable API does not eliminate delay, jitter, loss or application bugs. The route and connection quality need runtime observation. Keep transport status and gameplay readiness as different diagnostics so “connected” does not imply both target registries are synchronised.

Avoid promising a particular route or latency from a successful invite screenshot. Confirm both PCs/accounts, the driver/session state and the real feature sequence. The local records establish basic user-confirmed connection and narrower later local test results, not every later internet scenario.

A minimum invite/connection matrix

  • Host advertises a session only while joinable.
  • Guest accepts while the host is ready.
  • Guest accepts a stale invite after hosting ended.
  • Disconnect/reconnect creates a new session generation.
  • Range travel preserves or re-establishes the intended connection.
  • Wrong protocol/native bridge versions produce a clear incompatibility result.
