Workshop UI

Reuse the game’s widgets, but create your own controls and callbacks.

Find the workshop

The observed HUD class is /Game/UI/HUD/Workshop/HUD_Workshop.HUD_Workshop_C. Its attachment editor is WeaponEditMOde, with that exact spelling.

The HUD and attachment editor are related but have different lifetimes. A button placed on the HUD canvas needs its visibility tied to entering and leaving attachment edit mode.

Create a native button

The common TheRangeButton_C class provides the game’s existing button appearance. This creates a separate widget; it does not click or duplicate Save and exit:

local H = require("UEHelpers")

ExecuteInGameThread(function()
    local pc = H.GetPlayerController()
    if not pc or not pc:IsValid() then return end
    local class = LoadAsset("/Game/UI/Common/TheRangeButton.TheRangeButton_C")
    if not class or not class:IsValid() then return end
    local library = StaticFindObject("/Script/UMG.Default__WidgetBlueprintLibrary")
    local button = library:Create(pc, class, pc)
    if not button or not button:IsValid() then return end
    button.Text = FText("My action")
    button.NavText:SetText(FText("My action"))
    -- Add button to your valid parent panel and retain a reference.
end

Place the control

For a CanvasPanel parent, add with AddChildToCanvas and set the resulting CanvasPanelSlot’s anchors, alignment, position and size. Position numbers are relative to the anchors, not always screen pixels from the top left.

A local workbench check found Save and exit at X=50, Y=-50, size 200×40, with bottom-left anchors and bottom alignment. A button directly above it used Y=-100, leaving a ten-unit gap. Those numbers describe that HUD layout, not every resolution or future build.

Don’t copy action delegates

Copy appearance properties deliberately, not the original widget’s action bindings. A copied Save and exit delegate can execute the original action when your new button is pressed.

One local implementation handled the left-mouse keybind and checked the native button’s hover state. That verified a mouse path only; it does not establish controller, keyboard, touch or accessibility support. Prefer a verified button event route when your loader and widget expose one.

Rebuilds and input

Prevent duplicate construction by checking that your widget still has a valid parent. Hide it outside edit mode, cancel pending actions when the displayed weapon changes, and restore any input mode or cursor state you changed.

Test hover, click, closing the menu and opening it again. A widget object existing in memory does not prove that it is visible or clickable.

Walkthrough: add a control without stealing another action

1. Observe the normal editor lifecycle

Open and close attachment edit mode normally. Log HUD construction, edit-mode entry/exit and editor refreshes. Determine which parent panel survives an attachment change. If the point canvas is cleared during refresh, a button placed inside it may be removed with the points.

2. Create a fresh widget

Use the native button class for appearance, but instantiate it separately. Set its text and supported appearance fields deliberately. Do not clone the original HUD button’s delegates or use a raw object copy that carries a Save and exit callback into your new action.

Keep a strong, reachable reference through the owning widget tree/panel while the control is displayed. A local Lua variable that falls out of scope is not your complete UI ownership strategy.

3. Understand the canvas coordinates

With bottom-left anchors, negative Y positions move upward relative to the bottom edge. Alignment determines which point of the widget is placed at that coordinate. Copy anchors, alignment and size together before calculating a vertical offset.

Test the actual black menu bounds at more than one window size. Changing only X/Y can look correct at one resolution while breaking when the canvas scales or the text changes.

4. Make installation idempotent

Before creating another button, check whether the existing widget is valid and still parented. Reuse it when possible. If the original panel was rebuilt, attach a replacement once and update the stored reference.

Idempotent means repeating the setup produces one control in the correct state, not another copy of it.

5. Bind one action and a busy state

Disable the control while a queued operation is active. Recheck the editor/weapon context inside the operation. On completion, cancellation or Lua failure, update the text and enabled state consistently.

If your only verified input method is a hovered-button mouse check, document that limitation. A visible native button does not automatically give your custom Lua action keyboard/controller support.

6. Tie visibility to edit mode

Hide the control on edit-mode exit and cancel pending work that depends on that mode. Re-entry should restore the appropriate enabled state, not always assume a previous job succeeded. Check behaviour when the player switches weapons without leaving the HUD.

Native button construction, matching canvas layout, duplicate prevention and edit-mode visibility passed local fixtures.
