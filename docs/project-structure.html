Organising a mod

Keep startup, settings, engine access and feature state in separate places.

1. Decide what each file owns

For a small feature, four files are often enough. This is a practical starting point rather than a rule that every function needs its own module.

FileResponsibility
main.luaValidate startup settings and register callbacks once.
config.luaReturn defaults a user can edit with the game closed.
log.luaProvide a consistent message prefix.
inspect.luaRead engine state and return a result.

The weapon inspector walkthrough uses exactly this layout. For a larger mod, group related modules under folders such as ui/ and gameplay/ rather than growing main.lua into every subsystem.

2. Return a module

-- Scripts/counter.lua
local Counter = {}

function Counter.create()
    local state = {value = 0}
    function state:add(amount)
        self.value = self.value + amount
    end
    return state
end

return Counter
local Counter = require("counter")
local first = Counter.create()
local second = Counter.create()
first:add(2)
print(first.value .. ", " .. second.value .. "\n")

The output should be 2, 0. Returning a constructor lets two features have separate state without copying module code. Keep the module’s public operations small; callers shouldn’t need to reach into every internal field.

3. Validate settings before registering work

local Config = require("config")
assert(type(Config.Enabled) == "boolean", "Enabled must be a boolean")
assert(type(Config.MaxParts) == "number", "MaxParts must be a number")
assert(Config.MaxParts % 1 == 0, "MaxParts must be an integer")
assert(Config.MaxParts >= 1 and Config.MaxParts <= 64,
    "MaxParts must be from 1 to 64")

Explain each setting in the installation guide and pick bounded defaults. A typo should produce a useful log message, not an enormous actor loop or an unexplained half-initialised feature.

Do not store live actor or widget objects in a user configuration file. A persisted preference can survive travel; a world-owned object usually cannot.

4. Keep dependencies one-way

Have main.lua import the feature module and supply configuration. Avoid a feature importing main.lua to ask for a value while main.lua is still loading that feature. Pass a callback or state object instead.

require normally caches a loaded module within its Lua environment. Editing a module on disk does not prove that a running instance has reloaded it. Use the full restart workflow that was validated for your loader, and log a version string to identify the code actually running.

5. Separate three kinds of state

  • Configuration: user choices, limits and feature switches.
  • Session state: a custom round, network epoch or queued action.
  • World state: controllers, actors, widgets and cached components.

A single “reset everything” function can erase preferences unnecessarily. Reset world caches on travel, cancel actions when their context changes, and reset round scores only when the round flow calls for it.

6. Keep names portable

Use consistent filename casing and relative module names. Avoid a personal absolute install path inside a shared script. Keep mod-owned data under a deliberate data directory, not the current working directory by accident.

If you change a module’s name, update its requires and the release archive’s explicit file list together. Test an upgrade from the old release: a removed module left on disk can mask a packaging mistake.

Check the refactor

  1. Confirm the same startup message appears once.
  2. Trigger the feature and compare behaviour with the previous version.
  3. Use an invalid setting and check the diagnostic.
  4. Disable the feature and confirm no action callback is registered.
  5. Restart after removing an obsolete module to confirm nothing secretly depends on it.
