Checking game updates

Treat an update as a fresh compatibility check, not an automatic reason to change code.

Record the build

Write down the Steam build ID, executable version, UE4SS version/commit and your mod version. Keep a copy of the previous release so you can distinguish a new game change from a changed script.

The local demo records used build 26083142 and a UE5.7 release-branch executable. These are recorded reference points, not a claim that the reader’s installed game is that build.

Check the integration surface

AreaCheck
HooksFunction exists, class is loaded, signature and callback parameters still match.
PropertiesField type and generated name still match; don’t reuse an old offset.
AssetsExpected class, mesh, material and sound actually load.
UIConstruction, input, layout, close/reopen and duplicate prevention.
GameplayEquip, fire, hit, switch weapon, restart and travel.
SavesRead-only checks first; controlled write/restore tests on a disposable profile.

Test in stages

  1. Launch the loader without your feature enabled.
  2. Enable the mod and confirm clean startup.
  3. Trigger one relevant callback and inspect its arguments.
  4. Use the actual menu or gameplay feature.
  5. Repeat operations that rebuild objects or travel worlds.
  6. Run separate multi-PC tests for a multiplayer feature.

Stop changing code once a check passes unless there is a new failure or unresolved concern. A large refactor during a compatibility audit makes the result harder to interpret.

Record what passed

Keep test descriptions specific: “registered eight hooks” is different from “both peers fired and hit the same target”. Record the test method and its limits along with the result.

The recorded October demo update passed local menu, travel, model and synthetic gameplay checks. The real two-PC scenarios still had a narrower verified scope. Those two facts can coexist.

Report a regression

Include reproduction steps, exact content names, version details, a fresh relevant log excerpt and what changed from the last working build. Remove personal paths and IDs before posting logs publicly.

If you cannot reproduce a reported issue, preserve the report and the tested limits. Don’t mark it fixed because an unrelated synthetic case passed.
