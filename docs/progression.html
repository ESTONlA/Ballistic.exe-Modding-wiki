Ownership & unlocks

“Visible”, “unlocked”, “purchased” and “fitted” are different states.

The relevant containers

Game-instance fieldObserved representation
PurchasedPartsSet of soft class references for purchased parts.
UnlockedWeaponsArray of soft weapon-class references.
UnlockedRangesArray of range row names.
SavedWeaponTemplatesMap containing saved weapon assemblies.

A template can contain part paths that aren’t matched by a purchased-set-only check. That does not prove those paths all represent independently owned, currently available attachments.

Why simple filters fail

Three local attachment-menu experiments illustrate the problem:

  • A button-enabled check let every entry through, so enabled state did not express ownership.
  • PurchasedParts alone matched far fewer menu entries than the player expected.
  • A union of purchased and saved-template paths still missed expected choices in the live menu.

Those filters were not a completed ownership API. They were removed from the stable expanded catalog.

Match reference types

Passing a loaded UClass directly to a soft-reference set caused a native crash in an earlier filter. An isolated class-to-soft-reference conversion probe was safe for one unrelated class, but that did not validate every menu membership check.

Inspect the stored type, the API’s expected type and the exact path form. Package paths, object paths and generated Blueprint class paths are related but not identical strings.

Design an owned-only menu

  1. Define whether “owned” includes default, bought and currently fitted parts.
  2. Start with a small set of attachments whose ownership the player can confirm.
  3. Compare those parts with the game’s normal menu.
  4. Use stable identifiers and explain each exclusion in a diagnostic log.
  5. Test pagination after filtering, including an empty result and a single page.

Do not present “we found many save paths” as proof the filter is correct. The list the player can actually select is the test that matters.

Unlocking content

Adding an unlocked row name in memory can make a menu card appear. It doesn’t establish permanent progression, the presence of the associated map, or correct save persistence. A production unlock mod needs those checks separately.

Walkthrough: investigate one missing owned part

1. Define “owned” for the feature

Write down whether the list includes default parts, explicitly purchased parts, parts fitted to saved templates and content merely available in the shop. Those definitions can produce different correct lists. Get the expected rule clear before implementing membership.

2. Build a tiny ground-truth set

Pick a few named parts the player can demonstrate as bought or fitted, plus a few definitely unowned parts. Capture their normal menu entries and the relevant saved/live representations. A 137-entry filtered catalog is harder to debug than six known examples.

3. Record stored types and path forms

PurchasedParts uses soft class references in the inspected game instance; an attachment widget can expose a loaded class. Compare these representations deliberately. Record the package/object/generated-class path instead of normalising all strings by blindly deleting _C.

A native container membership call can be binding-sensitive. The prior wrong-type call crashed the process; a Lua pcall is not a native pointer-safety mechanism.

4. Explain every inclusion decision

part=<stable path>
normal_menu_state=<observed state>
matched_purchased=<yes/no/not checked>
matched_saved_template=<yes/no/not checked>
is_default=<known/unknown>
final_decision=<include/exclude/unknown>
reason=<specific rule>

Represent unknown explicitly while investigating. Quietly treating an unreadable reference as unowned hides exactly the case you need to inspect.

5. Validate the live list

Open multiple real attachment points, compare the expected named parts, switch tabs and fit one allowed part. Then check an unowned control. A plausible save-index count does not establish correct live filtering.

Counts are not correctness

In the local experiments, purchased-only membership and a larger union with template paths both produced unexpectedly small lists. The player’s expected part names remained the deciding test. Avoid promising six pages just because an index contains enough paths; several paths can refer to content not represented by the current menu.

Persistence check

If you change an unlock container in memory, leave and re-enter the menu, then restart using a disposable save. Determine whether the change was transient or persisted by a game action. Do not advertise permanent unlocking from a successful in-memory card visibility check.
