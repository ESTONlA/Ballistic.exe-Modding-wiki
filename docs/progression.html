Ownership & unlocks

“Visible”, “unlocked”, “purchased” and “fitted” are different states.

The relevant containers

Game-instance fieldObserved representation
PurchasedPartsSet of soft class references for purchased parts.
UnlockedWeaponsArray of soft weapon-class references.
UnlockedRangesArray of range row names.
SavedWeaponTemplatesMap containing saved weapon assemblies.

A template can contain part paths that aren’t matched by a purchased-set-only check. That does not prove those paths all represent independently owned, currently available attachments.

Why simple filters fail

Three local attachment-menu experiments illustrate the problem:

  • A button-enabled check let every entry through, so enabled state did not express ownership.
  • PurchasedParts alone matched far fewer menu entries than the player expected.
  • A union of purchased and saved-template paths still missed expected choices in the live menu.

Those filters were not a completed ownership API. They were removed from the stable expanded catalog.

Match reference types

Passing a loaded UClass directly to a soft-reference set caused a native crash in an earlier filter. An isolated class-to-soft-reference conversion probe was safe for one unrelated class, but that did not validate every menu membership check.

Inspect the stored type, the API’s expected type and the exact path form. Package paths, object paths and generated Blueprint class paths are related but not identical strings.

Design an owned-only menu

  1. Define whether “owned” includes default, bought and currently fitted parts.
  2. Start with a small set of attachments whose ownership the player can confirm.
  3. Compare those parts with the game’s normal menu.
  4. Use stable identifiers and explain each exclusion in a diagnostic log.
  5. Test pagination after filtering, including an empty result and a single page.

Do not present “we found many save paths” as proof the filter is correct. The list the player can actually select is the test that matters.

Unlocking content

Adding an unlocked row name in memory can make a menu card appear. It doesn’t establish permanent progression, the presence of the associated map, or correct save persistence. A production unlock mod needs those checks separately.
