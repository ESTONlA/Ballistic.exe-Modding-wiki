Timers & cleanup

Make a small mod behave properly after menu changes, travel and repeated clicks.

Pick a timing source

Use a slow discovery loop to wait for assets, a game-thread callback for engine work, and a game clock for elapsed-time calculations. They solve different problems.

TaskApproach
Wait for a widget classA bounded or low-frequency discovery loop.
Read or change Unreal objectsRun the operation on the game thread.
Animate an overlayUse elapsed time; don’t tie speed to callback count.
Expire a notificationCompare timestamps rather than assuming an exact timer interval.

Avoid overlapping work

A background loop can queue a new callback before the previous one has run. Keep one pending callback and clear the flag even after a Lua error:

local queued = false

LoopAsync(1000, function()
    if queued then return end
    queued = true

    ExecuteInGameThread(function()
        local ok, err = pcall(function()
            -- Read or update the current world's objects here.
        end)
        queued = false
        if not ok then print("[MyMod] " .. tostring(err) .. "\n") end
    end)
end

Cancel stale actions

For a queued attachment operation, capture the weapon identity and an operation number when the user clicks. Before every delayed step, check that the same editor is open, the weapon is unchanged and the operation number still matches. Stop when any check fails.

Setting a Lua boolean doesn’t cancel a callback already in the queue. The callback needs to check that boolean before doing engine work.

Separate world state from settings

Keep preferences such as overlay size separate from actor references. On world change, clear actor/widget caches, pending shot IDs and world-specific timers. Rebuild them from the new world. An object name alone can be reused after travel; a world identity plus object identity is a better cache key.

Clean up what you create

Track only the actors and widgets your mod creates. Remove its widgets from their parents and destroy its actors while they are still valid in that world. Don’t run a global actor sweep and delete everything with a similar class name.

If you temporarily change an existing actor’s visibility, collision or physics, remember its original values and restore those values when your feature closes.

Walkthrough: make a cancellable job

Use this pattern for work spread over multiple callbacks, such as clearing an attachment list one point at a time. The example below is pure Lua state; it does not remove attachments.

local generation = 0
local current = nil

local function begin(contextId)
    generation = generation + 1
    current = {id = generation, context = contextId, cancelled = false}
    return current
end

local function stillCurrent(job, contextId)
    return current == job and not job.cancelled
        and job.id == generation and job.context == contextId
end

local function cancel()
    generation = generation + 1
    if current then current.cancelled = true end
    current = nil
end

1. Capture the context when starting

Use the current world and weapon/menu identity to construct contextId. If an action is already pending, reject a second click or cancel the old action explicitly. Do not queue several identical destructive jobs because the button still looks enabled.

2. Validate inside the delayed callback

A check made before scheduling only proves the context was valid at scheduling time. Check stillCurrent inside the callback, then reacquire the editor and weapon. If the user left the menu or switched guns, stop before touching an attachment.

ExecuteWithDelay schedules asynchronous work in the local API used here. The engine operation should still be dispatched onto the game thread. The nominal delay is not a promise that the callback runs at an exact instant.

3. Perform one bounded operation

Process one point or a small fixed batch. If that changes the menu’s point list, return and reacquire on the next step. Mark a target done only when the intended action is accepted; otherwise keep a bounded retry policy and a visible failure result.

4. Finish every path

Success, cancellation and Lua failure should all release the pending state and update the UI. A “Clearing…” button that never re-enables after an error is a lifecycle bug even if the underlying removal succeeded.

If the feature owns a hook, widget or actor, give that object a specific teardown path. Merely dropping the Lua variable does not guarantee that an engine delegate or panel stops referencing it.

Clock and unit checklist

Write milliseconds or seconds in the variable name when it helps. ExecuteWithDelay’s integer delay and GetRealTimeSeconds do not use the same unit. Use a single clock for an elapsed-time calculation; don’t subtract an os.time wall-clock value from a world-relative game clock.

When a world clock restarts, reset any next-update deadline and interpolation history using it. A negative time delta can otherwise keep an update gated for an unexpectedly long time.

Acceptance test

  1. Start the job and confirm only one pending operation exists.
  2. Click again and confirm your documented duplicate-click behaviour.
  3. Change context before the next step and confirm no further action occurs.
  4. Force a Lua failure in a disposable test callback and confirm the busy state clears.
  5. Travel and confirm the old job cannot act on the new world.

What was checked
