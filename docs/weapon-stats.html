Recalculation

The Blueprint weapon base has UpdateCharacteristicsFromParts. Its nine boolean inputs in the inspected build are:

Weight, Ergo, CenterMassLoc, Recoil, GripCenter, BarrelLength,
EquippedScopeAndLaser, Cooling, TotalLength

This is a mutating recalculation function. Confirm the signature in your own dump before calling it. Prefer observing the normal attachment action first, rather than forcing a recalculation on every frame and masking a broken refresh chain.

A removal test

A local Sten fixture used a barrel strap and nested ergonomic broom grip. The grip’s modifier was approximately +0.15. Ten fit/remove cycles with the expanded compatibility hook active gave:

StepInstalled ergo
Rail-only baseline−0.600000
Grip fitted−0.450000
Grip removed−0.600000

That fixture started negative and returned to the same negative baseline. It did not show a cumulative penalty. It was a synthetic assembly, so those numbers are not the correct expected totals for every player’s Sten.

Report a stat bug

Include weapon/rail/attachment names, all three snapshots, game and loader versions, and whether the result survives leaving the workbench or restarting. Compare ordinary and expanded compatibility where possible.

Don’t clamp every negative number to zero. That can hide legitimate penalties and conceal the actual bug.

Walkthrough: diagnose a reported stat penalty

1. Fix the context

Record the game build, loader version, gun class, rail class, child attachment class and grip/stance state. Current ergonomics can differ from an installed total; comparing different fields or different grips can create a false apparent regression.

Use a disposable known assembly. Keep the normal baseline before expanding compatibility so the comparison is meaningful.

2. Take three snapshots

Capture the same fields in the same context at three points: rail present with no tested child; tested child fitted; tested child removed. Record the actual numbers to enough precision to see small changes.

local function compare(before, fitted, removed, epsilon)
    local bonus = fitted - before
    local residue = removed - before
    return {
        fittedDelta = bonus,
        removalResidue = residue,
        returnedToBaseline = math.abs(residue) <= epsilon
    }
end

local result = compare(-0.6, -0.45, -0.6, 0.00001)
assert(result.returnedToBaseline)

The fitted delta describes the child’s observed contribution in that setup. The removal residue is the quantity to investigate for an accumulated penalty. Its sign alone is not sufficient; compare its size with the baseline and an appropriate tolerance.

3. Repeat without masking the refresh path

Run several fit/remove cycles through the normal action. Do not manually recalculate after every removal if the question is whether the normal refresh is broken. That could make the symptom disappear without fixing the action chain.

Capture a separate “manual recalculation” experiment only if needed, and label it clearly. If manual recalculation restores the baseline but ordinary removal does not, the refresh path becomes a focused investigation target.

4. Compare three lifetimes

Check the value immediately after the action, after leaving/re-entering the editor, and after a restart using a disposable saved assembly. A stale displayed label, a stale live aggregate and a persisted template error can produce similar-looking screenshots while requiring different fixes.

What a conclusion can say

If all repeated removals match the starting value within tolerance, say that the tested setup returned to baseline. If another player still has a different assembly, keep that report open until its exact setup is reproduced. If a residue appears, identify which field and lifecycle first diverged before writing a clamp or an extra subtraction.

What was checked
