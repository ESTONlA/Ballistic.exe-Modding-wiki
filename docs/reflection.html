Reflection, classes & instances

Understand what Lua can see, which object you found and why a C++ name may not be callable.

The four objects to keep separate

Start with four distinct ideas: an asset package, a generated class, a class default object and a live instance. The workbench gun is an instance. Its class describes its type. A default object supplies class defaults. None of those is interchangeable with a string containing a package path.

QuestionWhat you need
What kind of gun is this?The live object’s class.
What is the player editing?The editor’s current live weapon.
Which defaults does this type use?The class default object, inspected deliberately.
Can the game load this content?The actual cooked asset and its dependencies.

A matching class name is a starting point, not proof that you selected the right live object. The range pawn and workbench can reference different guns at the same time. Record the current world and the selection reason beside your object name.

1. Check the reflected surface

UE4SS exposes reflected Unreal properties and functions through its bindings. A function mentioned in C++ documentation is not automatically callable from Lua. Inspect the exact owning class and loaded function before writing the call. The local TrivialObject failures are a practical example of why this check matters.

Use the object-dump workflow to identify a member, then a small read-only callback to observe it. Avoid guessing offsets or using an address from an old process. The UObject binding reference describes the current API; compare it with your installed loader.

2. Inspect identity before values

-- Context: object is a valid live UObject on the game thread.
local class = object:GetClass()
print("[MyMod] Object: " .. object:GetFullName() .. "\n")
if class and class:IsValid() then
    print("[MyMod] Class: " .. class:GetFullName() .. "\n")
end

Log the full object name, not just the display label. Two widgets may show the same text while belonging to different menus. A runtime suffix can identify an instance during a session, but it is not a permanent save key or a cross-PC identity.

3. Check inheritance deliberately

A derived Blueprint can inherit a property, override a function or add another event path. Find the declaring class and the actual runtime class. Registering a base hook and a derived hook may observe one action twice; failing to handle a derived target can miss it entirely.

local expected = StaticFindObject("/Script/Ballistic.C_WeaponBase")
if expected and expected:IsValid() and object:IsA(expected) then
    print("[MyMod] This is a weapon-base instance.\n")
end

Passing IsA establishes type compatibility, not readiness for a particular action. A weapon can have the right base class but no selected ammunition, a missing child assembly or an uninitialised menu context.

4. Separate read, call and write

Reading a numeric property, calling a getter, assigning a property and invoking a gameplay action are different operations. A property setter may bypass the normal action’s refresh, bookkeeping and save logic. A function that sounds like a refresh may also change derived gameplay state.

Build a research note with the member’s owner, reflected type, expected context, observed result and whether it changed anything. When moving from inspection to mutation, add explicit action ownership, cancellation and recovery rather than putting a setter into an always-running discovery loop.

Verify your interpretation

  • Find the object in the actual menu or range.
  • Read class and identity before the member.
  • Trigger the normal game action once and compare before/after values.
  • Repeat after a menu rebuild or world travel.
  • Keep dump-only findings separate from operations exercised on a live object.
