Reading & backing up saves

Start read-only. A live game instance and a save file are not the same snapshot.

Save location

The local demo uses %LOCALAPPDATA%/Ballistic/Saved/SaveGames/BallisticDemo.sav. Close the game and copy the save folder somewhere separate before an experiment that can change progression or assemblies.

Keep backups out of your mod release and out of a public repository. A useful backup is a dated copy you can identify and restore, not a file overwritten on every test.

Load without applying

GameplayStatics can load the persisted slot into a save object. Loading it for inspection is different from replacing the game instance’s active state:

local H = require("UEHelpers")

ExecuteInGameThread(function()
    local viewport = H.GetGameViewportClient()
    if not viewport or not viewport:IsValid() then return end
    local world = viewport:GetWorld()
    if not world or not world:IsValid() then return end
    local gameplay = StaticFindObject("/Script/Engine.Default__GameplayStatics")
    local instance = gameplay:GetGameInstance(world)
    if not instance or not instance:IsValid() then return end
    local save = gameplay:LoadGameFromSlot("BallisticDemo", instance.UserIndex)
    if save and save:IsValid() then
        print("[MyMod] Save class: " .. save:GetClass():GetFullName() .. "\n")
    end
end

Known save class

/Game/BlueprintLogic/Core/Game/Save/BallisticSaveGame.BallisticSaveGame_C

Do not assume that copying properties from one object to another is a complete restore. The local save-service code also refreshes game-instance data and invalidates selected loadouts and cached range lists after applying a snapshot.

Snapshot versus live state

A file copy contains the last persisted state. Unsaved workbench edits or in-memory progression can differ. “Host save to guest” is a one-way snapshot transfer unless you explicitly implement a merge or ongoing replication.

A sharing feature should distinguish accepting a download from applying it. Bind the final confirmation to the exact peer and transfer, reject incompatible data, back up the guest’s original file, and handle failed loads with a recovery path.

Verify a save feature

Use disposable profiles for write tests. Record a file hash before a read-only probe and compare it afterwards. For a restore feature, test a controlled backup/apply/restore cycle and then restart the game. A success message from a copy operation does not prove the game can load the result.

Walkthrough: inspect without applying

1. Make an identifiable backup

Close the game, copy the save folder to a separate dated location and keep the original filenames. Record the source file’s size, modification time and checksum if your test needs to prove no file changed.

A backup stored beside a release staging folder can accidentally be shipped. Keep private save material outside the build allowlist and review the archive contents before sharing.

2. Decide which state you want to inspect

LoadGameFromSlot reads the persisted slot. The game instance contains current in-memory state. If the player edited a gun but has not saved, the two can legitimately differ. Describe the chosen snapshot in the tool’s UI and logs.

3. Read the class before the fields

Use the read-only loading example, confirm the resulting class and inspect a small known field. Do not immediately assign the loaded object to CurrentSaveGame or call a retrieval/apply function; that crosses from inspection into changing the active game state.

A field whose name appears in a binary save is a discovery hint. It is not by itself a complete schema or proof that a byte-level edit will remain loadable.

4. Compare before and after

For a read-only probe, compare the original file checksum after the test and note any ordinary in-game actions that could have saved independently. For a write test, use a disposable profile and record exactly which operation changed the file.

Designing a snapshot transfer

StageRequired distinction
OfferHost identifies a bounded last-saved snapshot.
Accept downloadGuest consents to receive bytes, not to overwrite progression.
Receive / verifyLength, format, transfer identity and integrity are checked.
Apply confirmationGuest explicitly confirms applying this exact transfer from this peer.
Backup / replaceOriginal local data is preserved before replacement.
Reload / refreshGame state and cached selections are updated or recovery is triggered.

Do not call a one-time file snapshot “shared live progression”. It does not merge simultaneous changes or keep both saves continuously identical.

Applying and recovering

Apply only in a stable context, with travel and another transfer blocked. Bind the confirmation to the transfer ID so a delayed click cannot apply a newly arrived offer accidentally. If the imported state fails to load, restore the preserved backup and report the failure.

After a successful reload, invalidate cached selected weapons, unlocked range lists and UI data that were derived from the previous save. A correct file on disk can still leave the current menu showing stale selections.

What to test before releasing a save feature

Test valid input, malformed input, oversized input, interruption, reconnect, cancelled acceptance, repeated apply confirmation and failed load/recovery. Then restart and confirm the disposable profile loads. Local transfer simulation can validate a state machine without proving a real guest’s backup/apply flow.
