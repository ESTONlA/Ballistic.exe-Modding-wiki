Laser dots & material parameters

Work with the game’s projected laser dot and its material instead of replacing the laser attachment.

What was checked locally

The Laser Colors investigation spawned the pistol and Picatinny laser actors in isolated native tests. Laser_Base_C.LaserPointer was a DecalComponent using /Game/Materials/Decals/Lasers/LaserDecal_Master.LaserDecal_Master. Creating its dynamic material and reading/writing LaserColor passed on both actors. Repeated application reused the material; replacement, toggling, garbage collection and respawn checks passed.

The synthetic wall screenshots did not show either the baseline laser or a separate control decal. They therefore did not verify the visible green, purple, orange or blue hues. Keep that visual limit attached to the result; a successful RGBA readback is not a screenshot test.

Laser_Base_C reference

The archive also contains Laser_BasicPistolLaser and Laser_PicatinnyMountable. Their asset presence does not mean either is purchased in the current save. A colour mod should affect an existing equipped laser without granting one.

Inspect before modifying

-- Context: laser is a valid live Laser_Base_C-derived actor.
local dot = laser.LaserPointer
if dot and dot:IsValid() then
    local material = dot:GetDecalMaterial()
    if material and material:IsValid() then
        print('[LaserInspect] ' .. material:GetFullName() .. '\n')
    end
end

A parent material is not a per-instance override. Changing a shared asset or a class default can affect unrelated users of the same object. The local mod instead creates a dynamic instance owned by the decal component.

Change the exposed parameter

-- Context: dot is a valid laser DecalComponent, on the game thread.
local dynamicClass = StaticFindObject('/Script/Engine.MaterialInstanceDynamic')
local material = dot:GetDecalMaterial()
if material and material:IsValid() and dynamicClass:IsValid() then
    if not material:IsA(dynamicClass) then
        material = dot:CreateDynamicMaterialInstance()
    end
    if material and material:IsValid() then
        material:SetVectorParameterValue(FName('LaserColor'),
            {R = 0.02, G = 1.0, B = 0.04, A = 0.0})
    end
end

The parent LaserColor readback was (1, 1, 1, 0); the component’s separate DecalColor was (1, 1, 1, 1). Those are different values on different objects. Preserve an established alpha convention instead of assuming an opaque UI swatch uses the same shader input.

Make application survive normal play

  1. Resolve only currently loaded laser actor classes; avoid force-loading every weapon asset on startup.
  2. Skip default/template actors and invalid components.
  3. Reuse an existing MID instead of allocating a new one on every scan.
  4. Compare current channels before writing, and keep engine work on the game thread.
  5. Reacquire actors after attachment changes or travel. A newly built attachment has a new component and may need its own MID.
  6. Keep one colour version installed so separate timers do not overwrite each other.

Check the visible result

First confirm that the unmodified laser dot is visible on the chosen in-game surface. Then install one colour, restart, equip the same laser and use the same surface and viewing distance. Compare hue, brightness, toggle behaviour and newly equipped attachments. If both modified and baseline dots are invisible, diagnose the test setup before changing global exposure or decal settings.

Epic’s material-instance documentation explains the general parameter model. The parameter name and native results here come from the local game investigation.
