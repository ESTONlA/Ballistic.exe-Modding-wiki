Your first mod

Create a mod folder, write one Lua file, and check that it runs.

Create the folder

Inside your loader’s Mods folder, create MyFirstMod. Add a Scripts folder and an empty file named enabled.txt.

ue4ss/Mods/
└── MyFirstMod/
    ├── enabled.txt
    └── Scripts/
        └── main.lua

Enable file extensions in Windows Explorer so the script isn’t accidentally saved as main.lua.txt.

Write the script

Open main.lua in a text editor and add:

local function log(message)
    print("[MyFirstMod] " .. message .. "\n")
end

log("Loaded successfully.")

Use a distinct prefix in every log message. It makes your output easy to find when several mods are enabled.

Run the mod

  1. Save the file.
  2. Fully close and restart the game.
  3. Open ue4ss/UE4SS.log.
  4. Search for [MyFirstMod] Loaded successfully.

If the message appears, your script is loading. If it doesn’t, check the folder names and the log’s Lua errors.

Add a keybind

This example logs a message when you press F9. Choose a key that does not conflict with another mod.

RegisterKeyBind(Key.F9, function()
    print("[MyFirstMod] F9 pressed.\n")
end
Keep engine work on the game thread

A log message is a small first test. If your keybind changes Unreal objects, schedule that work with ExecuteInGameThread. See Finding game objects.

Disable or share the mod

With the game closed, remove the mod’s enabled.txt to disable it. For a small Lua-only release, package your mod folder, scripts and enable marker with clear installation instructions. Don’t bundle the game, saves, logs or your entire UE4SS installation.

Walkthrough: prove each stage separately

1. Check the real filenames

In Explorer, enable file-name extensions. Create main.lua as a text file and check the final extension after saving. A file named main.lua.txt can look correct when extensions are hidden, but it is not the expected entry script.

The enable marker belongs next to Scripts, not inside it. The Scripts directory belongs inside your mod folder. Verify those three relationships before changing Lua code.

2. Understand when the file runs

Top-level Lua statements execute when the loader starts the mod. A function definition creates a function; it does not execute its body until called. RegisterKeyBind stores a callback that will run later. Put the startup message outside that callback so you can distinguish “file loaded” from “key pressed”.

3. Add a counter to the key callback

local presses = 0
RegisterKeyBind(Key.F9, function()
    presses = presses + 1
    print(string.format("[MyFirstMod] Press count: %d\n", presses))
end)

Restart and press once, then again. Expect counts one and two. If each press prints two messages, check for duplicate registrations or a second enabled copy of the mod before blaming input timing. The counter is in-memory; restarting resets it.

4. Introduce a game-thread boundary

RegisterKeyBind(Key.F9, function()
    ExecuteInGameThread(function()
        print("[MyFirstMod] Game-thread callback reached.\n")
    end)
end)

This still only logs. It teaches where future engine calls belong without introducing object lookup at the same time. Execution is scheduled, so don’t assume the result exists synchronously on the line after ExecuteInGameThread returns.

5. Test disabling

Close the game, remove the enable marker and launch again. Your startup prefix and key response should be absent. If they remain, find the running copy by its startup version/path and check for another installed folder. Do not delete arbitrary files while the process is active.

What to build next

Read Lua basics if the syntax is unfamiliar. Use Organising a mod to add a configuration module. Then follow Build a weapon inspector for a complete read-only feature instead of a context-dependent fragment.

Your completion check for this page is small and concrete: one startup line, one increment per chosen input, no callback when disabled, and a log from the current process. Nothing here proves that a weapon or widget is ready yet.
