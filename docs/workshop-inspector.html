Build a weapon inspector

A complete, read-only example that connects settings, keybinds, game-thread work and weapon inspection.

What you will build

Press one key to print a snapshot to UE4SS.log: the current world, the equipped weapon or visible workbench-editor candidates, selected raw stats and a bounded list of child actors. The example contains no attachment setter, score award, save/apply operation or travel action.

Download the WorkshopInspector example. You can also open the individual source files below. This is teaching code adapted from the recorded local demo patterns, not a guarantee for every game or UE4SS build.

Before you start

  • A working UE4SS installation and a known log location.
  • The first mod startup check completed.
  • An unused key; the example defaults to F9.
  • A workbench attachment editor or a gun equipped in a range.

Close the game while creating or editing files. Keep this folder separate from other mods; do not merge its scripts into another mod’s Scripts folder.

1. Create the layout

ue4ss/Mods/WorkshopInspector/
├── enabled.txt
├── README.md
└── Scripts/
    ├── main.lua
    ├── config.lua
    ├── log.lua
    └── inspect.lua

The archive uses a mod-folder root. Extract it into ue4ss/Mods, not into Scripts and not into a second WorkshopInspector directory. Check that the final path ends in WorkshopInspector/Scripts/main.lua.

2. Add configuration

return {
    Enabled = true,
    KeyName = "F9",
    MaxParts = 12,
    MaxEditors = 8
}

Open config.lua. Enabled is a boolean. KeyName names an entry in the loader’s Key table. MaxParts limits printed child names; it does not remove parts or limit the actual assembly. MaxEditors bounds the number of loaded editor candidates inspected.

These limits are deliberately small so a key press does not produce an unbounded log dump. Change them with the game closed and restart to load the new values.

3. Add a logger

local Log = {}

function Log.info(message)
    print("[WorkshopInspector] " .. tostring(message) .. "\n")
end

return Log

Open log.lua. One function gives every message the same prefix. tostring makes diagnostics tolerant of nil and non-string values. The newline is the Lua escape \n, not an actual line break inside the quoted source string.

4. Read engine state

local H = require("UEHelpers")
local Inspect = {}

local function valid(object)
    if object == nil then return false end
    local ok, result = pcall(function() return object:IsValid() end)
    return ok and result == true
end

local function object(value)
    if valid(value) then return value end
    local ok, result = pcall(function() return value:get() end)
    if ok and valid(result) then return result end
end

local function name(value)
    if not valid(value) then return "<unavailable>" end
    return value:GetFullName() or "<unnamed>"
end

function Inspect.capture(config)
    local lines = {}
    local function add(text) lines[#lines + 1] = text end
    local viewport = H.GetGameViewportClient()
    if not valid(viewport) then return {"Viewport is not ready."} end
    local world = viewport:GetWorld()
    if not valid(world) then return {"World is not ready."} end
    add("World: " .. name(world))

    local gameplay = StaticFindObject("/Script/Engine.Default__GameplayStatics")
    if not valid(gameplay) then return {"GameplayStatics is unavailable."} end
    local pc = gameplay:GetPlayerController(world, 0)
    if not valid(pc) then
        add("Local controller is not ready.")
        return lines
    end

    local function describe(gun, label)
        if not valid(gun) then return end
        add(label .. ": " .. name(gun))
        for _, field in ipairs({"TotalErgo", "TotalInstalledErgo", "TotalRecoilControlModifier"}) do
            local ok, value = pcall(function() return gun[field] end)
            if ok and type(value) == "number" then
                add(string.format("  %s = %.6f", field, value))
            else
                add("  " .. field .. " = <unavailable>")
            end
        end
        local children = {}
        gun:GetAllChildActors(children, true)
        add("  Child actors reported: " .. tostring(#children))
        for i = 1, math.min(#children, config.MaxParts) do
            local child = object(children[i])
            if child then add("  Part " .. i .. ": " .. name(child)) end
        end
        if #children > config.MaxParts then add("  Remaining part names omitted by MaxParts.") end
    end

    local described = 0
    local pawn = pc:K2_GetPawn()
    if valid(pawn) then
        local ok, gun = pcall(function() return pawn.EquippedWeapon end)
        if ok and valid(gun) then describe(gun, "Equipped weapon"); described = described + 1 end
    end

    local editors = FindAllOf("WeaponEditMOde_C") or {}
    for i = 1, math.min(#editors, config.MaxEditors) do
        local editor = object(editors[i])
        if editor then
            local ok, visible = pcall(function() return editor:IsVisible() end)
            if ok and visible then
                add("Visible editor candidate: " .. name(editor))
                describe(editor.CurrentWeapon, "Workbench weapon")
                described = described + 1
            end
        end
    end
    if described == 0 then add("No equipped gun or visible workshop editor found.") end
    add("Snapshot finished. No parts, stats or saves were changed by this example.")
    return lines
end

return Inspect

Open inspect.lua. Read this module in four stages:

  1. Resolve the world. The viewport supplies the active world. A missing world produces a diagnostic result, not an attempt to use an invalid object.
  2. Resolve local context. GameplayStatics returns local controller zero. A pawn without EquippedWeapon is normal in some menus.
  3. Describe a gun. The module reads three numeric fields independently, then lists child actors up to MaxParts. An unavailable field is reported without writing a replacement value.
  4. Inspect editor candidates. Loaded visible WeaponEditMOde widgets can point at a workbench gun. A visible candidate is not proof of unique focus; several can be reported.

The wrapper helper accepts an ordinary valid UObject or tries to unwrap a parameter wrapper. The validity helper catches Lua failures while checking a reference. Neither helper protects against every native memory error, so the code still reacquires context for each snapshot instead of caching it across travel.

5. Wire startup and the keybind

local Config = require("config")
local Log = require("log")
local Inspect = require("inspect")

assert(type(Config.Enabled) == "boolean", "Enabled must be true or false")
assert(type(Config.KeyName) == "string" and Key[Config.KeyName], "KeyName is not a known key")
for _, field in ipairs({"MaxParts", "MaxEditors"}) do
    local value = Config[field]
    assert(type(value) == "number" and value % 1 == 0 and value >= 1 and value <= 64,
        field .. " must be an integer from 1 to 64")
end

if not Config.Enabled then
    Log.info("Disabled in config.lua.")
    return
end

local queued = false
RegisterKeyBind(Key[Config.KeyName], function()
    if queued then return end
    queued = true
    ExecuteInGameThread(function()
        local ok, result = xpcall(function()
            return Inspect.capture(Config)
        end, debug.traceback)
        queued = false
        if not ok then Log.info("Snapshot failed: " .. tostring(result)); return end
        for _, line in ipairs(result) do Log.info(line) end
    end)
end)

Log.info("Example loaded. Press " .. Config.KeyName .. " while the game is focused.")

Open main.lua. Startup validates settings before registering work. The key callback sets a pending flag and queues engine access on the game thread. The flag is released whether the Lua operation succeeds or fails. The logger prints the collected result only after the snapshot function returns.

This prevents overlapping queued snapshots. It is not a general-purpose task cancellation system. There is no automatic retry loop because the next key press reacquires the current world and objects.

6. Run and interpret the output

  1. Start the game and find [WorkshopInspector] Example loaded. in the log.
  2. Open the workbench attachment editor or equip a gun in a range.
  3. Focus the game window and press the configured key once.
  4. Search for the next [WorkshopInspector] World: message.
  5. Compare object names and raw field values, not just the number of printed lines.
[WorkshopInspector] World: <current world full name>
[WorkshopInspector] Equipped weapon: <live weapon full name>
[WorkshopInspector]   TotalErgo = <raw numeric value>
[WorkshopInspector]   TotalInstalledErgo = <raw numeric value>
[WorkshopInspector]   Child actors reported: <count>

The workbench route reports a visible editor candidate and a Workbench weapon instead of requiring an Equipped weapon line. A negative raw stat is not automatically a bug; see Weapon stats.

7. Troubleshoot

ResultNext check
No startup lineCheck enabled.txt, filename extensions, archive root and the fresh loader log.
Key does nothingFocus the game; check the configured key and conflicts; confirm main.lua loaded.
Viewport/controller not readyWait until the game has entered a playable menu or range, then press again.
No weapon/editor foundOpen the actual attachment editor or equip a gun; inspect build-specific class names.
Stat unavailableConfirm that field exists on the actual weapon class in your build.
Snapshot failedRead the traceback; isolate the operation before changing the rest of the module.

8. Extend one thing at a time

A useful next step is to collect two snapshots and compare a stat before and after a normal attachment action. Keep only ordinary Lua values, not live actor pointers, in that comparison. Report a changed world or weapon as a different context rather than subtracting unrelated values.

For a UI overlay, keep capture separate from rendering and bound its update rate. For a release, follow Packaging a Lua mod. Do not turn this read-only example into an automatic mutation script without adding a clear action, cancellation and recovery flow.

Verification limits

The game-facing names and integration patterns come from local demo source and earlier native checks. Any mock checks of these files only validate the Lua/control flow they exercise; they do not prove that an actual workbench widget or a future build returns the same data. Use Test a mod step by step to record a real run.
