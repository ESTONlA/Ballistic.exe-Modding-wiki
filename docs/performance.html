Performance & profiling

Measure the expensive boundary between Lua and the engine before changing update rates.

1. Make a baseline

Record the game scene, mod configuration and action sequence. Compare the same range and weapon with the feature disabled and enabled. A different target layout or gun assembly can change workload enough to invalidate the comparison.

Separate idle cost from action cost. A UI might be cheap while closed but hitch when rebuilding every widget after a click. An actor registry might be cheap to update but expensive to rediscover.

2. Count work before timing it

local counters = {discoveries = 0, samples = 0, setters = 0}

local function report()
    print(string.format(
        "[MyMod] discoveries=%d samples=%d setters=%d\n",
        counters.discoveries, counters.samples, counters.setters
    ))
end

For an unchanged menu, how many labels are set again each second? For a static target, how often do you reload its mesh? A counter often exposes redundant work before a profiler is needed.

Report periodically, not on every frame. Logging can become part of the hitch you are trying to diagnose.

3. Give tasks different cadences

WorkReasonable starting approach
Find loaded classesSlow retry until ready; stop once installed.
Rediscover a target registryOccasional refresh plus world-change invalidation.
Update known moving actorsBounded frequent samples.
Render interpolated visualsA local visual cadence independent of network sends.
Capture weapon meshesOn identity changes, with a slower periodic verification.

These are design starting points, not universal tick rates. Measure your scene and adjust the budget. Reducing cosmetic updates must not silently reduce gameplay-event reliability.

4. Avoid catch-up bursts

A stalled frame can leave several nominal deadlines behind. For a cosmetic update, replaying all missed steps in one frame makes the stall worse. Advance from elapsed time and cap work instead.

local nextUpdate = nil
local lastNow = nil

local function shouldUpdate(now, rate)
    local period = 1 / rate
    if not nextUpdate or not lastNow or now < lastNow then
        nextUpdate = now
    end
    lastNow = now
    if now < nextUpdate then return false end
    nextUpdate = math.max(nextUpdate + period, now + period * 0.1)
    return true
end

Call this with one coherent clock. The backwards-clock branch matters after a world reset when a world-relative clock starts over. A setting change should explicitly reset the schedule too, rather than waiting on a deadline calculated for the old rate.

5. Reuse unchanged engine objects

Cache asset references after successful loading. For a weapon proxy, compare the mesh identity before replacing an actor. For a menu, compare the intended text, enabled state and visibility with the last successful values before issuing setters.

Only mark a cached value as applied after the setter succeeds. If a native operation fails, caching the desired value too early can prevent the retry that would restore the UI.

6. Budget large registries

Process a fixed number of ordinary targets per update and carry a cursor forward. Prioritise moving or recently hit targets separately, with its own cap. Without the second cap, “priority” can grow into another unbounded full-world pass.

Keep event queues bounded and define backpressure. Silently dropping a cosmetic sample is different from dropping an acknowledged hit or save-transfer chunk.

Verify the improvement

Repeat the baseline sequence, compare counters, and check that the feature still works after travel, a missing object and a setter failure. Faster code that displays stale state is not a successful optimisation.
