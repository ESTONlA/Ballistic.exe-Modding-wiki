Know which changes can reuse game assets and which need an asset pipeline.

Lua-only mods

Lua is useful for changing behaviour, creating UI and assembling objects from assets already cooked into the game. You can prototype layouts by spawning existing meshes and components in the current world.

That does not create a new cooked map. The scene still belongs to the existing world, with its lighting, streaming and lifecycle.

New models and textures

An external .fbx file is a source model, not a game-ready Unreal asset. A Lua script cannot simply use an FBX path as a normal skeletal mesh reference.

Proper mesh, material and animation integration generally needs compatible cooked assets or a dedicated runtime importer. This wiki does not provide an importer.

Opening the game in Unreal

The installed game contains cooked content, rather than the developer’s editable source project. Installing Unreal Editor does not restore the original Blueprints, levels or source assets.

The local executable reported the UE5.7 release branch. That is useful context when investigating tools, but it does not establish that any specific editor patch will produce compatible content.

Testing a runtime scene

  • Check mesh and material availability in the actual game build.
  • Test lighting and exposure in the world where you spawn objects.
  • Verify collision and a safe player spawn.
  • Keep references to the actors your mod owns.
  • Remove them when the scene closes or the world changes.

For a runtime prototype, start with Range menus & travel and Timers & cleanup. For distributing an asset-free Lua mod, see Packaging a Lua mod.

Walkthrough: choose the smallest content pipeline

1. Does the change need a new asset?

If the goal is a stat display, a menu action or rearranging existing targets, start with runtime scripting and existing cooked assets. You avoid a cooking pipeline and can verify the behaviour before investing in new art.

If the goal is a genuinely new weapon model with correct materials, collision and animation, list those requirements explicitly. A replacement mesh preview satisfies only one part of that list.

2. Inventory available assets

Use a browser such as FModel to look for relevant classes, meshes, materials and sounds. Then verify a small set can actually load in the game. A thumbnail or menu row is evidence of a reference, not proof the full asset and its dependencies are usable.

3. Build a runtime prototype

Spawn one object, confirm its transform, mobility and visibility, then add collision and interaction. Keep a handle to it for cleanup. Expand to a small layout only after the one-object case is visibly correct.

For procedural geometry, the local records established that the procedural mesh component API could create a triangle and a runtime texture import could load a PNG. Those API checks did not establish a correctly lit, textured and positioned RPG model on a held weapon. Keep the capability claim that narrow.

4. Check lighting in the actual world

A detached runtime scene still inherits the hosting world’s rendering environment. If structures render but are very dark, inspect sky/ambient lighting, material response and postprocess settings instead of assuming a view-distance problem. A bright emissive workaround is not equivalent to a complete outdoor lighting setup.

5. Use an asset pipeline when the requirement needs it

For cooked content, you need a compatible asset/cooking approach and a way to load the packaged result. The installed game is not the developer’s editable project. An engine branch string is context for compatibility research, not a complete reconstruction recipe.

Document the exact toolchain, asset types and load mechanism you actually tested. Don’t tell another modder that a particular editor patch will work based only on a matching major/minor version.

Acceptance checklist

Test appearance, scale, orientation, materials, collision, interaction, cleanup and travel separately. For a weapon, add handling, ammunition, firing and persistence. For a range, add spawn safety, targets, scoring and return flow. Decide which of those are actually in your prototype’s scope before calling it a finished mod.
